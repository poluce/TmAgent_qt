Turn Lifecycle

完整会话里，一次回合从用户输入到最终回复的执行图

这张图严格按从上到下的执行顺序，描述当前系统里一个完整回合如何被创建、排队、执行、进入工具链、收束为最终答复，以及在失败 / 取消时如何结束。完整会话就是多个这样的回合首尾相接。

`turnId`：回合主分组键 `requestTraceId`：整条链路追踪键 `runId`：当前执行实例键 工具调用不是新回合 右键卡片可复制；悬浮小组件可看详细定义

单次回合纵向流程

从上到下 = 实际执行顺序
01
用户输入

用户在当前会话里发送一条消息

入口是 `ChatService::enqueueUserMessageAs(...)`。这里先拿到会话、发送者、输入文本和可选的客户端消息 ID。

会话维度
`sessionId`
发送者
user / agent
输入内容
prompt 文本
客户端消息 ID
`clientMessageId`
02
回合创建

系统为这次输入创建回合标识

这里会生成并绑定 `requestTraceId`、`turnId`、`runId`。其中 `turnId` 是后续把用户消息、工具过程、最终答复归到同一回合的核心。

链路追踪
`requestTraceId`
回合主键
`turnId`
执行实例
`runId`
03
消息入链

用户消息先写入会话主链路

这条用户消息会被持久化进 `Session`，并带上 `traceId` 和 `turnId`。从这一步开始，这条消息已经属于某个明确回合。

消息对象
`Message`
持久化字段
`traceId` / `turnId`
04
排队 / 合并

决定是新回合，还是并入队列尾部已有回合

如果同一发送者在很短时间内连续补充消息，系统可能把它合并到队列尾部已有回合，而不是新建一个。所以“一个回合”本质上是执行单元，不一定严格等于一个聊天气泡。

条件一
同一发送者
条件二
时间窗口内
条件三
队列尾部可合并
05
开始执行

`TurnManager` 把 queued turn 提升为 active turn

这一步开始真正执行该回合。状态机会从 `queued` 进入 `running`，同时发出 `turn_started` 等执行事件。

06
上下文组装

组装本轮执行所需上下文

这里会加载对话历史、记忆上下文、活跃子任务、系统提示词等，然后把当前回合的 `turnId / traceId / runId` 注入运行时 IO 上下文。

记忆上下文
memory context
委派上下文
delegate context
系统提示词
system prompt
07
第一次模型请求

向模型发送本轮第一段请求

`LLMAgent::postRequestToServer(...)` 会记录第一段 request，并开始接收流式输出。注意：这只是“同一回合的第一段交互”。

运行记录
ioHistory 记录 request
回合归属
挂同一 `turnId`
08
模型分支判断

模型要么直接结束，要么先返回 `tool_calls`

这是整个回合最关键的分叉点：
- 直接给最终答复
- 先请求工具，再继续回合

分支 A：模型直接完成

  • 记录最终 response
  • 助手消息写入会话链路
  • 状态变为 `done`
  • 发出 `turn_completed`

分支 B：进入工具链

  • 先记录 `tool_calls` 响应
  • 执行工具
  • 回收工具结果
  • 再次请求模型
  • 最终拿到完整答复后才结束
09
工具链内部

工具调用和工具结果仍然属于同一个回合

工具调用不会创建新回合。工具调用消息、工具结果消息、工具后 follow-up request，全都沿用当前 `turnId / traceId`。

关键判断
工具调用 = 回合内部步骤
结论
不是新回合
10
再次请求模型

工具完成后，系统发起 follow-up request

这会在 `ioHistory` 里形成第二段 request/response，但它仍然和第一段共享同一个 `turnId`。执行记录页面现在按这个规则做回合聚合展示。

交互形态
同回合多段交互
页面规则
按 `turnId` 聚合
11
最终答复

助手最终回复写入会话链路

当最终内容拿到后，助手消息也会带上同一个 `traceId / turnId`，从而和用户消息、工具过程、事件统一归档到这一回合。

12
回合结束

更新任务状态、发事件、做后处理

回合收束时，会更新 `task_state`、发出 `turn_completed` / `turn_failed`，并继续进入记忆 retain / reflect、心跳状态、日志链路等后处理。

13
异常结束

如果失败或取消，也仍然是同一个回合的结束方式

无论是模型错误、工具失败，还是用户手动中断，都不会“另起一个回合”，而是把当前回合标记为 `failed / canceled`。

失败路径
`turn_failed`
取消路径
`canceled`
14
页面聚合

执行记录页面按回合聚合展示

页面现在是按 `turnId` 把一条回合内的多段 request/response、工具调用、工具结果和事件聚成一条“执行记录”，而不是拆成几条半截日志。

页面视角
默认看回合级别
展开方式
再看内部细节
15
进入下一轮

用户继续说话，就会开始下一个回合

一个完整会话并不是一个回合，而是多个回合串起来：当前回合结束 → 用户再次输入 → 新建下一个 `turnId` → 重复整条流程。

你需要记住的 4 件事

1. 一个回合 = 一个完整执行单元
不是简单的一问一答，而是从用户输入到最终结果 / 失败 / 取消的整段闭环。

2. `turnId` 是主分组键
用户消息、工具调用、工具结果、最终回复，都靠同一个 `turnId` 串起来。

3. 工具调用不是新回合
工具前请求、工具后 follow-up request，只是同一回合里的多段模型交互。

4. 完整会话 = 多个回合首尾相接
每次用户再次输入，通常都会开始新的回合；这些回合共同构成整个会话。

页面设计启发
执行记录页面不该以“单次 request/response”为主阅读单位，而应该以回合级执行单元为主单位：默认看回合，展开看该回合内部的多段交互、工具过程和证据层。
