# TmAgent 项目愿景与产品规划

> 本文档是 TmAgent 项目的顶层纲领，定义产品的终极形态、核心理念和演进路线。
> 所有后续的技术设计、架构决策和功能开发都应以本文档为目标对齐。
> 状态：active（规范，唯一产品愿景源）

---

## 一、一句话定义

**TmAgent 是一个模拟真人协作方式的多智能体工作台。**

每个 Agent 像一个真人一样拥有自己的身份、会话列表和工作视角，Agent 之间通过对话协作完成任务，用户可以切换到任意 Agent 的视角观察其工作状态。

---

## 二、核心隐喻：像真人一样协作

TmAgent 的产品设计基于一个现实世界的隐喻：

> 一个人与外界交流时，使用的是聊天工具（微信、飞书等）。
> 两个人协作时，他们各自在自己的聊天工具里与对方交流。
> 每个人有自己的会话列表、自己的消息记录、自己的工作视角。

TmAgent 将这个模型映射到 Agent 世界：

| 现实世界 | TmAgent |
|---------|---------|
| 一个人 | 一个 Identity（用户或 Agent） |
| 一个人的岗位/职责 | 岗位 Agent（持久存在，有记忆和经验） |
| 一个人用电脑/手机完成具体工作 | 子 Agent（临时创建，完成后销毁，结果汇报给岗位 Agent） |
| 微信/飞书 | QChatWidget 聊天界面 |
| 聊天列表里的每个对话 | 与不同 Identity 的会话（Session） |
| 切换账号 | 顶部 Tab 切换 Identity 视角 |
| 每个人有自己的聊天记录 | 每个 Identity 有自己的会话管理系统 |
| 私聊 | 两个 Identity 之间的 Private Session |
| 拉群协作 | 多个 Identity 在同一个 Group Session 中协作 |
| 群主/管理员 | Session 的 owner，拥有邀请/移除成员的权限 |
| @某人 | 消息中的 mentions 字段，指定消息的目标接收者 |
| 公司的共享文件夹/网盘 | 文件库（FileStore） |
| 公司的知识库/Wiki | 知识库（KnowledgeBase） |
| 员工的技能/特长 | Skill 库（SkillRegistry） |
| 公司采购的 SaaS 工具 | MCP 服务器（MCP Server Registry） |
| 员工的工作经验 | 经验库（ExperienceStore） |
| 出差时用手机远程办公 | 外部通讯渠道插件（微信/飞书/Telegram 等接入） |
| 公司的 IT 基础设施可扩展 | 插件系统（PluginManager） |

这个隐喻贯穿整个产品设计，是理解 TmAgent 的钥匙。

## 三、岗位 Agent 与子 Agent：双层架构

### 3.1 核心问题

如果会话列表中的每个 Agent 只是一个"一次性工具"——用户发一条消息，Agent 完成任务，对话结束——那它和普通的 ChatGPT 没有本质区别。上下文会被塞满，没有记忆，无法积累经验，用户每次都要从零开始。

TmAgent 的解法来自现实世界的观察：

> 你的同事（比如一个开发工程师）是一个**持久存在的人**。
> 领导给他派任务，他不是用脑子硬算——他打开电脑，用 IDE 写代码，用终端跑命令，用浏览器查资料。
> 电脑、IDE、终端是他的**工具**，用完就关，但他本人还在。
> 他从每次任务中积累经验，下次遇到类似问题会更快更好。

映射到 TmAgent：

```
现实世界                              TmAgent
─────────                            ────────
开发工程师（人）                →     岗位 Agent（持久存在，有记忆）
电脑/IDE/终端（工具）           →     子 Agent（临时创建，完成后销毁）
工程师用电脑完成任务后关机      →     子 Agent 完成任务后汇报结果，然后销毁
工程师记住了这次的经验          →     岗位 Agent 将结果内化为经验/记忆
下次遇到类似任务，工程师更熟练  →     岗位 Agent 基于记忆做出更好的决策
```

### 3.2 两层定义

#### 岗位 Agent（Positional Agent）

出现在用户会话列表和顶部 Tab 中的 Agent。它是一个**持久的身份**。

特征：
- **持久存在**：不会因为一次任务结束而消失
- **有记忆**：记住与用户和其他 Agent 的所有对话历史
- **有经验**：从历史任务中提取和积累经验知识
- **有岗位职责**：有明确的角色定义（架构师、开发者、测试员等）
- **轻量上下文**：自身不执行具体的工具调用，上下文只包含对话和决策，不会被工具调用的细节塞满
- **可对话**：用户和其他 Agent 可以直接与它对话

#### 子 Agent（Worker Agent）

岗位 Agent 在执行具体任务时临时创建的"工具"。它是一个**临时的执行单元**。

特征：
- **临时创建**：岗位 Agent 接到任务后按需创建
- **任务完成即销毁**：执行完毕后将结果汇报给岗位 Agent，然后销毁
- **无记忆**：不保留历史，每次都是全新的上下文
- **有完整工具权限**：可以调用文件操作、Shell、LSP、Web 等工具
- **上下文专注**：只包含当前任务的相关信息，不会被无关历史干扰
- **不可直接对话**：用户和其他岗位 Agent 不直接与子 Agent 交互

### 3.3 工作流程

```
用户 → 岗位 Agent（架构师）：请分析 src/core/ 的架构问题

岗位 Agent 内部决策：
  1. 这个任务需要读取大量代码文件并分析
  2. 如果我自己做，上下文会被代码内容塞满
  3. 创建一个子 Agent 去执行具体的代码分析工作

岗位 Agent 创建子 Agent：
  ┌─────────────────────────────────────────┐
  │  子 Agent（临时）                         │
  │  任务：分析 src/core/ 的架构问题          │
  │  工具：view_file, grep_search, lsp, ...  │
  │                                          │
  │  [读取 20 个文件]                         │
  │  [调用 LSP 分析依赖关系]                  │
  │  [生成分析报告]                           │
  │                                          │
  │  → 汇报结果给岗位 Agent                   │
  │  → 销毁                                   │
  └─────────────────────────────────────────┘

岗位 Agent 收到子 Agent 的汇报：
  - 将分析报告的**结论**（而非 20 个文件的原始内容）纳入自己的上下文
  - 将关键发现内化为经验记忆
  - 向用户回复精炼的分析结果

用户看到的：
  架构师 Agent 回复了一份清晰的架构分析报告
  （用户不需要知道背后有子 Agent 在工作）
```

### 3.4 为什么需要双层

| 问题 | 单层 Agent 的困境 | 双层架构的解法 |
|------|------------------|---------------|
| 上下文溢出 | Agent 读了 20 个文件，上下文塞满，无法继续思考 | 子 Agent 承担文件读取，岗位 Agent 只接收精炼结果 |
| 无记忆 | 每次对话都是新的，用户要重复说明背景 | 岗位 Agent 持久存在，记住所有历史对话 |
| 无经验 | 同样的任务做第二次，效率不会提升 | 岗位 Agent 从历史任务中积累经验，越用越好 |
| 任务中断 | Agent 执行到一半上下文满了，任务失败 | 子 Agent 可以拆分为多个小任务，逐个完成汇报 |
| 多任务并行 | 一个 Agent 同时只能做一件事 | 岗位 Agent 可以同时创建多个子 Agent 并行执行 |

### 3.5 用户视角 vs 内部实现

**用户看到的**：

```
[用户 Tab]
会话列表：
  └─ 架构师 Agent

聊天区：
  用户：分析 src/core/ 的架构问题
  架构师：（思考中...）
  架构师：分析完成，发现以下 5 个架构问题：...
```

用户只与岗位 Agent 对话，体验上就像和一个有记忆的同事聊天。

**切换到架构师 Tab 后看到的**：

```
[架构师 Tab]
会话列表：
  ├─ 用户（对话）
  └─ [内部] 代码分析任务 #1（子 Agent 执行记录）

侧边面板：
  子 Agent 执行日志：
  ├─ 14:30 创建子 Agent，任务：分析 src/core/
  ├─ 14:30 子 Agent 调用 view_file("src/core/agent/LLMAgent.h")
  ├─ 14:31 子 Agent 调用 lsp("findReferences", "ToolDispatcher")
  ├─ ...（20+ 工具调用）
  ├─ 14:35 子 Agent 汇报结果
  └─ 14:35 子 Agent 销毁

  记忆/经验：
  ├─ "src/core/ 存在 4 个全局单例，耦合严重"
  └─ "AgentChatWidget 是 God Object，1560 行"
```

用户切换到架构师视角后，可以看到子 Agent 的完整执行过程，了解架构师是"怎么工作的"。

### 3.6 岗位 Agent 的记忆体系

岗位 Agent 的记忆分为三层：

```
岗位 Agent 的记忆
├── 对话记忆（短期）
│   └── 与用户和其他 Agent 的最近对话摘要
│       （不是原始消息，而是压缩后的关键信息）
├── 任务记忆（中期）
│   └── 每次子 Agent 执行任务后的结果摘要
│       例如："2026-02-08 分析了 src/core/，发现 4 个全局单例问题"
└── 经验知识（长期）
    └── 从多次任务中提炼的稳定结论和方法论
        例如："该项目偏好使用信号槽而非回调"
        例如："重构时应先写测试再改代码"
```

当岗位 Agent 收到新任务时，它会：
1. 检索相关的经验知识，作为决策参考
2. 回顾相关的任务记忆，避免重复工作
3. 结合当前对话上下文，决定如何拆解任务并创建子 Agent

这样，岗位 Agent 的上下文始终保持精炼——它只包含决策所需的信息，而不是 20 个文件的原始内容。

## 四、产品形态

### 4.1 界面结构

```
┌──────────────────────────────────────────────────────────────────┐
│  [用户(我)]  [Agent-A]  [Agent-B]  [Agent-C]  [+创建Agent]      │  ← 顶部 Tab 栏
├──────────────┬───────────────────────────────┬───────────────────┤
│              │                               │                   │
│  会话列表     │        聊天区                  │   侧边面板        │
│              │                               │   (可选)          │
│  ├─ Agent-A  │  [消息气泡]                    │   - Agent 信息    │
│  ├─ Agent-B  │  [消息气泡]                    │   - 工具日志      │
│  └─ Agent-C  │  [消息气泡]                    │   - 任务状态      │
│              │                               │                   │
│              │  [输入框]                      │                   │
├──────────────┴───────────────────────────────┴───────────────────┤
│  状态栏                                                          │
└──────────────────────────────────────────────────────────────────┘
```

### 4.2 Tab 切换机制

- **用户 Tab**（默认）：用户自己的视角，会话列表中是用户与各个 Agent 的对话
- **Agent Tab**：切换到某个 Agent 的视角，看到的是该 Agent 的会话列表、收到的消息、执行的任务
- 点击 Tab = 登录该 Identity 的账号，查看他的一切

### 4.3 用户创建 Agent 的流程

```
用户在自己的 Tab 中点击 [+创建Agent]
    │
    ▼
填写 Agent 配置（名称、角色描述、模型、工具权限等）
    │
    ▼
系统为该 Agent 生成一个完整的 Identity
    ├── 分配 UUID
    ├── 创建独立的会话管理系统
    ├── 初始化工具权限
    └── 在顶部 Tab 栏新增一个标签
    │
    ▼
用户的会话列表中自动出现"与该 Agent 的对话"
Agent 的会话列表中自动出现"与用户的对话"
```

## 五、核心数据模型

### 5.1 Identity（身份）

Identity 是系统中的第一公民。用户是一个 Identity，每个 Agent 也是一个 Identity。

```
Identity
├── id: UUID                          # 唯一标识
├── name: QString                     # 显示名称
├── type: User | Agent                # 身份类型
├── avatar: QString                   # 头像路径
├── profile: IdentityProfile          # 详细信息
│   ├── description: QString          # 角色描述（Agent 才有）
│   ├── systemPrompt: QString         # 系统提示词（Agent 才有）
│   ├── modelConfig: LLMConfig        # 模型配置（Agent 才有）
│   └── toolPermissions: ToolPerms    # 工具权限（Agent 才有）
├── memory: AgentMemory               # 记忆体系（Agent 才有）
│   ├── dialogSummaries: List<Summary>    # 对话记忆（短期）：近期对话的压缩摘要
│   ├── taskResults: List<TaskResult>     # 任务记忆（中期）：每次子 Agent 执行的结果摘要
│   └── experience: List<Experience>      # 经验知识（长期）：跨任务提炼的稳定结论
├── sessions: SessionList             # 该 Identity 的所有会话
└── events: EventLog                  # 该 Identity 收到的所有事件
```

### 5.2 Session（会话）

Session 是两个或多个 Identity 之间的对话通道。

```
Session
├── id: UUID                          # 会话唯一标识
├── participants: List<UUID>          # 参与者的 Identity ID 列表
├── type: Private | Group             # 私聊或群聊
├── owner: UUID                       # 会话创建者（群聊场景下即群主）
├── messages: List<Message>           # 消息历史（所有参与者共享同一份）
├── metadata: SessionMeta             # 会话元信息
│   ├── title: QString                # 会话标题（私聊自动取对方名称，群聊可自定义）
│   ├── avatar: QString               # 群头像（私聊取对方头像，群聊可自定义或自动拼接）
│   ├── createdAt: QDateTime          # 创建时间
│   └── lastActiveAt: QDateTime       # 最后活跃时间
└── state: SessionState               # 运行时状态（流式输出等）
```

**关键设计**：

- 会话是**共享的**。用户与 Agent-A 的对话，在用户的会话列表和 Agent-A 的会话列表中是**同一个 Session 对象**，不是两份拷贝。
- 每个 Identity 的会话列表是 Session 的**视图**，按该 Identity 的视角排序和过滤。
- **私聊**（Private）：participants 恰好两个 Identity，标题自动显示为对方名称。
- **群聊**（Group）：participants 两个以上 Identity，由 owner 创建，owner 可以邀请或移除成员。

### 5.3 Message（消息）

```
Message
├── id: UUID                          # 消息唯一标识
├── sessionId: UUID                   # 所属会话
├── senderId: UUID                    # 发送者的 Identity ID
├── mentions: List<UUID>              # @的目标 Identity 列表（群聊中指定接收者）
├── content: MessageContent           # 消息内容
│   ├── type: Text | ToolCall | ToolResult | System | File
│   ├── text: QString                 # 文本内容
│   └── payload: QJsonObject          # 结构化数据（工具调用参数、文件信息等）
├── timestamp: QDateTime              # 发送时间
└── status: Pending | Sent | Error    # 消息状态
```

### 5.4 数据关系总览

```
                    ┌─────────────┐
                    │  Identity   │
                    │  (用户/Agent)│
                    └──────┬──────┘
                           │ 1:N
                           ▼
                    ┌─────────────┐
                    │  Session    │◄──── N:M ────► Identity (参与者)
                    │  (会话)     │
                    └──────┬──────┘
                           │ 1:N
                           ▼
                    ┌─────────────┐
                    │  Message    │
                    │  (消息)     │
                    └─────────────┘
```

## 六、交互场景

### 场景 1：用户与单个 Agent 对话

最基础的场景，等同于当前已实现的功能。

```
[用户 Tab]
会话列表：
  └─ Agent-A (代码助手)

聊天区：
  用户：帮我重构这个函数
  Agent-A：好的，我来分析一下...
  Agent-A：[工具调用: view_file("src/main.cpp")]
  Agent-A：建议做以下修改...
```

### 场景 2：用户创建多个 Agent，分别对话

用户创建了多个专用 Agent，在自己的会话列表中分别与它们对话。

```
[用户 Tab]
会话列表：
  ├─ Agent-A (代码助手)      ← 负责写代码
  ├─ Agent-B (测试专家)      ← 负责写测试
  └─ Agent-C (架构师)        ← 负责设计评审
```

### 场景 3：用户切换到 Agent 视角观察

用户点击顶部 Agent-A 的 Tab，切换到 Agent-A 的视角。

```
[Agent-A Tab]
会话列表：
  ├─ 用户(我的创建者)        ← Agent-A 与用户的对话
  ├─ Agent-B (测试专家)      ← Agent-A 与 Agent-B 的协作对话
  └─ Agent-C (架构师)        ← Agent-A 与 Agent-C 的协作对话

聊天区（选中"与 Agent-B 的对话"）：
  Agent-A：我完成了 main.cpp 的重构，请帮我写单元测试
  Agent-B：好的，我来看看改动...
  Agent-B：[工具调用: view_file("src/main.cpp")]
  Agent-B：测试已生成，见 tests/test_main.cpp
```

用户在这个视角下可以：
- 查看 Agent-A 收到了哪些消息
- 查看 Agent-A 与其他 Agent 的协作过程
- 查看 Agent-A 执行了哪些工具调用
- 了解 Agent-A 的工作量和任务完成情况

### 场景 4：Agent 之间自动协作

用户下达一个复杂任务，主 Agent 自动拆解并委派给子 Agent。

```
[用户 Tab]
用户 → Agent-A：请重构 src/core/ 模块并补充测试

    Agent-A 内部决策：
    1. 创建与 Agent-B 的会话，委派测试任务
    2. 创建与 Agent-C 的会话，请求架构评审

[Agent-A Tab]                        [Agent-B Tab]
会话列表：                            会话列表：
├─ 用户 (收到任务)                    ├─ Agent-A (收到委派)
├─ Agent-B (委派测试)                 └─ ...
└─ Agent-C (请求评审)

[Agent-C Tab]
会话列表：
├─ Agent-A (收到评审请求)
└─ ...
```

### 场景 5：用户以管理者视角监控全局

用户通过切换不同 Agent 的 Tab，像一个管理者一样巡视每个"员工"的工作状态：

- Agent-A 正在与 Agent-B 讨论接口设计 → 进展正常
- Agent-C 的会话列表是空的 → 还没收到任务，可能需要分配工作
- Agent-B 的最近消息是一个错误 → 需要介入帮助

### 场景 6：群聊——多 Agent 在同一个会话中协作

用户或 Agent 创建一个群聊 Session，将多个相关 Agent 拉入同一个对话中。

**6a. 用户发起群聊**

```
[用户 Tab]
用户点击 [创建群聊]，选择 Agent-A(架构师)、Agent-B(开发者)、Agent-C(测试员)
群聊标题："src/core 重构项目组"

会话列表：
  ├─ Agent-A (私聊)
  ├─ Agent-B (私聊)
  ├─ Agent-C (私聊)
  └─ src/core 重构项目组 (群聊)    ← 新增

聊天区（群聊）：
  [系统消息] 用户 创建了群聊，邀请了 Agent-A、Agent-B、Agent-C
  用户：我需要重构 src/core/ 模块，架构师先出方案，开发者执行，测试员验收。
  Agent-A：好的，我先分析现有代码结构...
  Agent-A：@Agent-B 以下是重构方案，请按此执行：...
  Agent-B：收到，开始执行。
  Agent-B：@Agent-C 重构完成，请编写测试并验收。
  Agent-C：[工具调用: execute_command("cmake --build . && ctest")]
  Agent-C：@用户 全部测试通过，验收完成。
```

**6b. Agent 自主拉群**

Agent 在执行复杂任务时，判断需要多方协作，主动创建群聊。

```
[用户 Tab]
用户 → Agent-A：重构 src/core/ 并确保测试通过

    Agent-A 内部决策：
    这个任务涉及开发和测试，需要多方同步协作，创建群聊比私聊更高效。

[Agent-A Tab]
会话列表：
  ├─ 用户 (收到任务)
  └─ 重构协作群 (群聊)              ← Agent-A 自主创建

聊天区（重构协作群，成员：Agent-A、Agent-B、Agent-C）：
  [系统消息] Agent-A 创建了群聊，邀请了 Agent-B、Agent-C
  Agent-A：我收到用户的重构任务，分工如下：
           @Agent-B 负责代码修改
           @Agent-C 负责测试验收
           我负责方案设计和最终汇总。
  Agent-B：明白。
  Agent-C：明白。
```

**6c. 群聊中的 @机制**

群聊中的消息默认所有成员可见，但通过 @（mentions）机制指定消息的目标接收者：

- **@某个 Agent**：该 Agent 会将此消息作为需要处理的输入，触发其决策循环。未被 @的 Agent 可以看到消息但不会主动响应。
- **@所有人**：所有 Agent 都会处理此消息。
- **不 @任何人**：消息仅作为上下文记录，不触发任何 Agent 的主动响应。用户发言默认 @所有人。

这个机制解决了群聊中的关键问题：**避免所有 Agent 同时抢答**。只有被 @的 Agent 才会响应，其余 Agent 只是旁听，保持上下文感知但不产生噪音。

**6d. 用户在群聊中切换视角**

用户切换到 Agent-B 的 Tab，可以看到 Agent-B 视角下的群聊：

```
[Agent-B Tab]
会话列表：
  ├─ Agent-A (私聊)
  └─ 重构协作群 (群聊)              ← 同一个群，Agent-B 的视角

聊天区（重构协作群）：
  （消息内容与其他视角完全一致——因为是同一个 Session）
  但 Agent-B 的侧边面板显示的是 Agent-B 自己的：
  - 工具调用日志（只有 Agent-B 执行的工具）
  - 任务状态（Agent-B 负责的部分）
```

### 场景 7：群聊的典型协作模式

#### 模式 A：项目组模式（长期群）

用户为一个项目创建固定群组，所有相关 Agent 长期驻留，随时可以发起讨论。

```
"TmAgent 开发群"
成员：用户、架构师Agent、前端Agent、后端Agent、测试Agent
用途：日常开发协作，持续存在
```

#### 模式 B：任务群模式（临时群）

Agent 为某个具体任务创建临时群聊，任务完成后群聊归档。

```
"修复 #127 Bug"
成员：开发Agent、测试Agent
用途：修复特定 Bug，完成后归档
生命周期：任务开始 → 任务完成 → 自动归档
```

#### 模式 C：评审群模）

用户创建评审群，邀请多个 Agent 对同一份代码发表意见。

```
"架构评审：新版 Session 模型"
成员：架构师Agent、安全Agent、性能Agent
用途：用户 @所有人 提出方案，各 Agent 从自己的专业角度给出评审意见
```

## 八、架构原则

基于上述产品形态，以下原则指导所有技术决策：

### 原则 1：Identity 是第一公民

所有数据和行为都挂在 Identity 上。不存在"全局会话列表"或"全局 Agent 列表"——只有"某个 Identity 的会话列表"和"系统中所有 Identity 的注册表"。

### 原则 2：Session 是共享的，视角是独立的

两个 Identity 之间的对话只有一份 Session 数据，但每个 Identity 看到的是自己的视角（排序、未读状态、置顶等可以不同）。

### 原则 3：Agent 之间通过消息协作，而非函数调用

Agent-A 委派任务给 Agent-B，不是通过 `agentB.execute(task)`，而是通过在 Session 中发送一条消息。这保证了：
- 所有协作过程都有记录（消息历史）
- 用户可以切换到任意 Agent 视角查看协作过程
- 协作方式与用户和 Agent 的交互方式一致

### 原则 4：每个 Agent 是独立的运行单元

每个 Agent 有自己的：
- 模型配置（可以用不同的 LLM）
- 工具权限（可以访问不同的工具集）
- 会话列表（只看到与自己相关的对话）
- 事件日志（只记录自己相关的事件）

不共享业务全局状态。如果需要共享信息，通过消息传递。像 AgentEventBus 这类全局组件只承担事件传输基础设施，不承载业务数据或决策状态。

### 原则 5：岗位 Agent 不做具体工作，子 Agent 不保留记忆

岗位 Agent 是决策者和协调者，不直接调用文件操作、Shell 等工具。它通过创建子 Agent 来执行具体任务，自己只负责：
- 理解任务意图
- 拆解任务并创建子 Agent
- 接收子 Agent 的汇报结果
- 将结果精炼后回复给对话方
- 将关键结论沉淀为记忆和经验

子 Agent 是执行者，拥有完整的工具调用能力，但任务完成后即销毁，不保留任何状态。这保证了：
- 岗位 Agent 的上下文永远不会被工具调用细节塞满
- 子 Agent 每次都有干净的上下文，专注于当前任务
- 岗位 Agent 可以持久存在，跨越多次任务积累经验

### 原则 6：用户是特殊的 Identity

用户和 Agent 在数据模型上是对等的（都是 Identity），但用户有额外的权限：
- 创建和销毁 Agent
- 切换到任意 Agent 的视角
- 修改任意 Agent 的配置
- 介入任意 Session（以管理者身份）

### 原则 7：一切能力通过插件扩展

系统的核心是精简的框架，所有可变的能力（通讯渠道、工具集、Skill、MCP 服务）都通过插件机制接入。这保证了：
- 核心框架稳定，不因新增能力而频繁修改
- 第三方可以开发插件扩展系统能力
- 用户可以按需启用/禁用插件

管理项目相关的文件资源，提供统一的文件访问接口。

```
FileStore

│   ├── 文件索引和快速检索
│   ├── 文件版本追踪（与 Git 集成）
│   ├── 文件权限控制（按 Agent 限制可访问范围）
│   └── 临时文件管理（子 Agent 的工作产出）
└── 使用方式
    ├── 子 Agent 通过文件库读写文件（而非直接操作文件系统）
```

**与现实的对应**：公司的共享文件夹 / 网盘 / Git 仓库。

存储可复用的工作流程和方法论，Agent 可以学习和调用这些 Skill。

```
SkillRegistry
├── 存储内容
│   ├── 预定义 Skill（系统内置）

├── Skill 定义
│   ├── name: 技能名称
│   ├── description: 技能描述
│   ├── steps: 执行步骤（结构化的工作流）
│   ├── tools_required: 需要的工具列表
│   ├── risk_level: 风险等级（低/中/高）
│   └── applicable_roles: 适用的 Agent 角色
└── 使用方式
    ├── 岗位 Agent 根据任务类型选择合适的 Skill
    ├── 子 Agent 按 Skill 定义的步骤执行任务
    └── 用户可以创建/编辑/分享 Skill
```

**与现实的对应**：公司的 SOP（标准操作流程）/ 员工培训手册。新员工按 SOP 做事，老员工可以优化 SOP。

管理所有可用的 MCP（Model Context Protocol）服务，提供外部工具的统一接入。

```
McpServerRegistry
├── 存储内容
│   ├── 已注册的 MCP Server 列表
│   │   ├── GitHub MCP Server（代码仓库操作）
│   │   ├── Jira MCP Server（项目管理）
│   │   ├── Database MCP Server（数据库查询）
│   │   ├── 自定义 MCP Server
│   │   └── ...
│   ├── 每个 Server 提供的工具列表（自动发现）
│   └── Server 的连接配置和认证信息
├── 能力
│   ├── MCP Server 的注册/注销/健康检查
│   ├── 工具 Schema 的自动发现和缓存
│   ├── 按 Agent 权限过滤可用工具
│   ├── 连接池管理和故障恢复
│   └── 兼容主流 MCP 传输方式（stdio/http/sse）并适配市面主流 MCP Server

    ├── 子 Agent 通过 ToolDispatcher 调用 MCP 工具（透明，无需感知是本地还是远程）
    ├── 用户可以在设置中添加/配置 MCP Server
```

#### 经验库（ExperienceStore）

存储从历史任务中提炼的经验知识，是岗位 Agent 长期记忆的持久化存储。

```
ExperienceStore
├── 存储内容
│   ├── 任务结果摘要（每次子 Agent 完成任务后自动记录）
│   ├── 提炼的经验结论（从多次任务中归纳的稳定知识）
│   ├── 失败案例和教训（避免重复犯错）
│   └── 协作模式记录（哪些 Agent 组合在什么任务上效果好）
├── 经验条目结构
│   ├── id: UUID
│   ├── agentId: UUID                # 归属的岗位 Agent
│   ├── type: TaskResult | Insight | Lesson | Pattern
│   ├── content: QString             # 经验内容
│   ├── tags: List<QString>          # 标签（用于检索）
│   ├── confidence: float            # 置信度（多次验证的经验置信度更高）
│   ├── createdAt: QDateTime
│   └── lastUsedAt: QDateTime        # 最近被检索使用的时间
├── 能力
│   ├── 按相关性检索（语义匹配 + 标签过滤）
│   ├── 经验的自动提炼（从多条 TaskResult 中归纳 Insight）
│   ├── 经验的衰减和淘汰（长期未使用的经验降低优先级）
│   └── 跨 Agent 的经验共享（可选，需要显式授权）
└── 使用方式
    ├── 岗位 Agent 收到新任务时自动检索相关经验
    ├── 子 Agent 完成任务后，岗位 Agent 自动将结果摘要存入经验库
    └── 用户可以查看/编辑/删除经验条目
```

**与现实的对应**：员工的工作经验和个人笔记。老员工比新员工效率高，就是因为积累了经验。

### 9.3 资源库的存储方式

所有资源库的数据存储在本地，遵循以下原则：
- 知识库和经验库统一使用 SQLite，避免 JSON 在检索和并发写入场景下的性能瓶颈
- 知识库启用 FTS5 全文检索，语义检索的向量索引作为可选增强能力
- 文件库和 MCP 服务器配置保留轻量 JSON 格式，Skill 库保持 YAML 以便人工维护

```
~/.tmagent/                          # TmAgent 数据根目录
├── knowledge/                       # 知识库
│   ├── knowledge.db                 # SQLite（含 FTS5 索引）
│   ├── entries/                     # 知识原文（Markdown 文件，可选）
│   └── vectors/                     # 向量索引（用于语义检索，可选）

│   └── index.json                   # 文件索引和权限配置

├── experience/                      # 经验库
│   ├── experience.db                # SQLite（任务摘要、经验、教训、模式）
│   └── shared_policy.json           # 跨 Agent 共享授权策略
└── plugins/                         # 插件目录
    ├── channels/                    # 通讯渠道插件
    └── extensions/                  # 功能扩展插件
```

### 10.1 为什么需要插件系统

- 通讯渠道：微信、飞书、Telegram、Discord、Slack、邮件...
- 外部工具：GitHub、Jira、Notion、数据库、CI/CD...
- 模型接入：新的 LLM 厂商、本地模型、自定义模型...
- UI 扩展：自定义面板、可视化组件、主题...

不可能把所有这些都内置到核心框架中。插件系统让核心保持精简，能力通过插件无限扩展。

### 10.2 插件类型

```
插件系统
├── 通讯渠道插件（Channel Plugin）
│   ├── 职责：将外部通讯工具的消息桥接到 TmAgent 的 Session 中
│   ├── 示例：微信插件、飞书插件、Telegram Bot 插件、邮件插件
│   └── 接口：IChannelPlugin
│
├── 工具插件（Tool Plugin）
│   ├── 职责：为 Agent 提供新的工具能力
│   ├── 示例：数据库查询工具、图表生成工具、PDF 解析工具
│   └── 接口：ITool（复用现有接口）
│
├── 模型插件（Provider Plugin）
│   ├── 职责：接入新的 LLM 模型
│   ├── 示例：新厂商的 API 适配、本地模型接入
│   └── 接口：LLMProvider（复用现有接口）
│
└── 扩展插件（Extension Plugin）
    ├── 职责：扩展系统的其他能力
    ├── 示例：自定义 UI 面板、数据导出、自动化脚本
    └── 接口：IExtensionPlugin
```

### 10.3 插件生命周期

```
插件发现 → 加载 → 初始化 → 运行 → 停用 → 卸载

具体流程：
1. 发现：扫描 plugins/ 目录，读取每个插件的 manifest.json
2. 加载：动态加载插件的共享库（.dll / .so / .dylib）
3. 初始化：调用插件的 initialize() 方法，传入系统上下文
4. 运行：插件注册自己的能力（工具、渠道、Provider 等）
5. 停用：用户在设置中禁用插件，调用 shutdown()
6. 卸载：从系统中移除插件注册的所有能力
```

### 10.4 插件清单文件

每个插件目录下必须有一个 `manifest.json`：

```json
{
  "id": "com.example.wechat-channel",
  "name": "微信通讯渠道",
  "version": "1.0.0",
  "type": "channel",
  "description": "通过微信接收和发送消息，支持远程控制 Agent",
  "author": "TmAgent Community",
  "entry": "wechat_channel.dll",
  "dependencies": [],
  "permissions": ["network", "message_send", "message_receive"],
  "config_schema": {
    "wechat_hook_port": { "type": "integer", "default": 19088 }
  }
}
```

## 十一、外部通讯渠道

### 11.1 核心场景

> 用户的电脑在办公室运行着 TmAgent，Agent 们正在协作完成任务。
> 用户出门在外，需要查看进度或下达新指令。
> 用户打开手机上的微信/飞书/Telegram，给 TmAgent 发一条消息。
> TmAgent 收到消息后，将其路由到对应的 Agent，Agent 处理后通过同一渠道回复。

这就是外部通讯渠道的价值：**让用户在任何地方、通过任何通讯工具都能与自己的 Agent 团队交互**。

### 11.2 架构设计

```
外部世界                    TmAgent 桌面端
─────────                  ──────────────

微信 ──────┐
飞书 ──────┤               ┌──────────────────────┐
Telegram ──┼── 网络 ──────►│  ChannelManager       │
Discord ───┤               │  (通讯渠道管理器)      │
邮件 ──────┘               │                      │
                           │  ├─ WeChatChannel     │
                           │  ├─ FeishuChannel     │
                           │  ├─ TelegramChannel   │
                           │  └─ ...               │
                           └──────────┬───────────┘
                                      │
                                      ▼
                           ┌──────────────────────┐
                           │  MessageRouter        │
                           │  (消息路由器)          │
                           │                      │
                           │  外部消息 → Session    │
                           │  Session 回复 → 外部   │
                           └──────────┬───────────┘
                                      │
                                      ▼
                           ┌──────────────────────┐
                           │  Identity / Session   │
                           │  (正常的对话流程)      │
                           └──────────────────────┘
```

### 11.3 通讯渠道插件接口

```
IChannelPlugin
├── initialize(context)              # 初始化，传入系统上下文
├── start()                          # 启动监听（开始接收外部消息）
├── stop()                           # 停止监听
├── sendMessage(channelUserId, text) # 向外部用户发送消息
├── onMessageReceived(callback)      # 注册消息接收回调
└── getStatus() → ChannelStatus      # 获取连接状态

ChannelMessage（外部消息的标准化格式）
├── channelId: QString               # 渠道标识（"wechat" / "telegram" / ...）
├── channelUserId: QString           # 外部用户在该渠道的 ID
├── text: QString                    # 消息文本
├── attachments: List<Attachment>    # 附件（图片、文件等）
└── timestamp: QDateTime             # 消息时间
```

### 11.4 消息路由规则

外部消息进入 TmAgent 后，需要路由到正确的 Session：

```
外部消息到达
    │
    ▼
ChannelManager 接收并标准化为 ChannelMessage
    │
    ▼
MessageRouter 根据路由规则决定目标：
    │
    ├─ 规则 1：渠道用户已绑定某个 Identity
    │          → 路由到该 Identity 的对应 Session
    │
    ├─ 规则 2：消息包含 Agent 名称前缀（如 "@架构师 分析代码"）
    │          → 路由到指定 Agent 的 Session
    │
    ├─ 规则 3：默认路由
    │          → 路由到用户 Identity 的默认 Session
    │
    └─ 规则 4：未识别
              → 发送帮助提示，引导用户绑定或指定目标
```

### 11.5 安全考虑

外部通讯渠道引入了新的安全边界：

- **身份验证**：外部消息的发送者必须经过验证，防止未授权的人控制 Agent
- **权限控制**：通过外部渠道下达的指令可以设置权限级别（如只允许查看状态，不允许执行写操作）
- **消息加密**：敏感信息（代码、密钥等）不应通过不安全的渠道传输
- **速率限制**：防止外部渠道被滥用导致 Agent 过载
- **审计日志**：所有通过外部渠道的操作都记录在案

### 11.6 典型使用场景

**场景 A：手机远程查看进度**

```

TmAgent（微信）：架构师回复——重构进度 70%，Agent-B 正在执行代码修改，
                预计还需要完成 3 个文件的重构。当前无阻塞问题。
```

**场景 B：远程下达紧急指令**

```
用户（飞书）：@所有人 暂停当前任务，有紧急 Bug 需要修复，见 issue #234
TmAgent（飞书）：收到。已通知所有 Agent 暂停当前任务。
                架构师正在分析 issue #234...
```

**场景 C：接收任务完成通知**

```
TmAgent（Telegram）：[通知] 测试员 Agent 报告：
                     src/core/ 重构任务全部测试通过，验收完成。
                     详细报告已保存到文件库。
用户（Telegram）：好的，合并到 main 分支。
TmAgent（Telegram）：收到，开发者 Agent 正在执行 git merge...
```

## 十二、演进路线

### 阶段 0：当前状态（已完成）

- 单用户视角，扁平会话列表
- 每个会话绑定一个 Agent 实例
- AgentChatWidget 包揽所有逻辑
- 基础对话 + 工具调用 + 流式输出可用

### 阶段 1：架构重塑——引入 Identity 和 Session 模型

**目标**：将当前的扁平结构重构为 Identity-Session 模型，但暂时只有用户一个视角（不加 Tab）。

关键工作：
- 定义 Identity、Session、Message 数据结构
- 实现 IdentityManager（管理所有 Identity 的注册和生命周期）
- 实现 SessionManager（管理 Session 的创建、查询、持久化）
- 使用 UUID 作为会话主键，彻底替换“行号主键”
- 将 AgentChatWidget 拆分为 View 层 + Service 层
- 消息写入统一收口到 `SessionManager::postMessage()`，避免多入口并发写入
- 将全局单例改为按 Identity 实例化（每个 Agent 有自己的 ToolDispatcher 实例）

**验收标准**：
- 功能与当前完全一致，但底层数据模型已切换为 Identity-Session
- UI 仍保持单用户视角，不引入顶部 Tab 多视角交互
- 删除会话不再触发行号重排
- 工具权限具备按 Identity 的允许/拒绝校验链路

### 阶段 2：多视角——顶部 Tab 切换

**目标**：实现顶部 Tab 栏，用户可以切换到 Agent 视角。

关键工作：
- 顶部多视角组件采用 `QTabBar + QStackedWidget`（不使用 `QTabWidget`）
- Tab 切换时，会话列表和聊天区切换到对应 Identity 的数据
- Agent 创建流程（用户创建 Agent → 生成 Identity → 新增 Tab）
- Agent 视角下的只读/可操作权限控制
- IdentityView 懒加载与缓存回收策略
- 多 Tab 流式输出治理：仅可见 Tab 实时渲染，后台 Tab 只更新数据模型

**验收标准**：
- 用户可以创建 Agent，在顶部 Tab 切换视角，看到不同 Identity 的会话列表
- 用户 Tab 固定不可关闭，Agent Tab 可关闭
- Tab 切换延迟 <= 200ms（含后台流式刷新场景）
- 输入响应延迟 P95 <= 150ms（多 Tab 流式并发场景）

### 阶段 3：群聊与 Agent 间通信——消息驱动的协作

**目标**：支持私聊和群聊两种 Session 类型，Agent 之间可以通过消息协作。岗位 Agent 通过子 Agent 执行具体任务。

关键工作：
- **私聊**：Agent 主动创建与其他 Agent 的私聊 Session，发送消息委派任务
- **群聊创建**：用户或 Agent 可以创建群聊，选择多个参与者
- **群聊成员管理**：owner 可以邀请/移除成员，成员可以主动退出
- **@机制**：消息的 mentions 字段指定目标接收者，只有被 @的 Agent 触发决策循环
- **消息路由**：群聊中的消息广播给所有参与者，但只有被 @的 Agent 主动响应
- **子 Agent 执行机制**：岗位 Agent 接到任务后创建子 Agent 执行具体工作（文件操作、Shell、LSP 等），子 Agent 完成后汇报结果并销毁
- **结果精炼**：岗位 Agent 接收子 Agent 的原始结果，提取关键结论纳入自己的上下文，而非原始数据
- **并发预算控制**：通过 ConcurrencyController 限制全局/单岗位/单 Provider 并发配额
- **群聊归档**：任务完成后，临时群聊可以归档，保留历史但不再活跃

**验收标准**：
- 用户可以创建群聊并邀请多个 Agent
- 群聊中 @某个 Agent 时，只有该 Agent 响应
- Agent 可以自主创建群聊拉入其他 Agent 协作
- 用户可以在各 Agent Tab 中从不同视角查看同一个群聊

### 阶段 4：可观测性——调试与监控

**目标**：在 Agent 视角中集成调试面板，支持完整的任务追踪。

关键工作：
- Trace 体系落地（与 `docs/10_方案/10-架构升级设计方案.md` 的可观测性目标对齐）
- Agent Tab 侧边面板：工具调用日志、任务状态、决策追踪
- 全局任务视图：跨 Agent 的任务依赖关系和完成状态
- 时间轴回放

**验收标准**：用户可以在任意 Agent Tab 中查看该 Agent 的完整工作轨迹，包括工具调用、决策过程、与其他 Agent 的通信记录。

### 阶段 5：智能化——记忆与经验沉淀

**目标**：岗位 Agent 拥有持久记忆，能从历史任务中学习，越用越好。

关键工作：
- **对话记忆**：岗位 Agent 自动压缩历史对话为摘要，保持上下文精炼
- **任务记忆**：每次子 Agent 执行完毕，岗位 Agent 将结果摘要存入任务记忆
- **经验提炼**：从多次任务记忆中提炼稳定的结论和方法论，存入长期经验
- **经验检索**：岗位 Agent 收到新任务时，自动检索相关经验作为决策参考
- ExperienceManager 落地（与 `docs/10_方案/11-记忆系统规划方案.md` 的阶段 C/D 对齐）
- 任务模板：将成功的协作模式保存为可复用的模板
- 智能路由：根据任务类型自动选择最合适的 Agent 和模型组合
- 渐进式工具授权：按任务阶段动态调整 Agent 的工具权限

**验收标准**：
- 岗位 Agent 能记住之前的对话和任务结果，不需要用户重复说明背景
- 同样的任务第二次执行时，岗位 Agent 能基于经验做出更好的决策
- 系统能根据历史经验推荐协作方案

### 阶段 6：资源库体系

**目标**：建立五大资源库，为 Agent 提供知识、文件、技能、工具和经验的统一访问能力。

关键工作：
- **知识库**：实现知识条目的增删改查和检索（先关键词，后语义向量）
- **文件库**：实现文件索引、权限控制、变更通知，与 Git 集成
- **Skill 库**：定义 Skill 的 YAML 格式，实现内置 Skill 加载和自定义 Skill 管理
- **MCP 服务器**：实现 MCP Server 的注册、健康检查、工具自动发现（复用现有 McpToolProvider），并兼容市面主流 MCP Server
- **经验库**：实现经验条目的存储、检索、自动提炼和衰减机制
- **统一存储**：所有资源库数据持久化到 `~/.tmagent/` 目录

**验收标准**：
- 岗位 Agent 收到任务时能自动检索知识库和经验库获取相关信息
- 子 Agent 通过文件库读写文件，权限受控
- 用户可以在设置中管理所有资源库的内容

### 阶段 7：插件系统与外部通讯渠道

**目标**：实现插件框架，支持通讯渠道插件接入，用户可以通过外部通讯工具远程控制 Agent。

关键工作：
- **插件框架**：实现 PluginManager，支持插件的发现、加载、初始化、停用、卸载
- **插件接口**：定义 IChannelPlugin、IExtensionPlugin 等标准接口
- **通讯渠道管理器**：实现 ChannelManager，统一管理所有通讯渠道插件
- **消息路由器**：实现 MessageRouter，将外部消息路由到正确的 Session
- **身份验证**：外部渠道的用户身份验证和权限控制
- **首个渠道插件**：实现一个参考渠道插件（如 Telegram Bot），作为其他插件的开发模板

**验收标准**：
- 用户可以通过外部通讯工具（如 Telegram）向 Agent 发送指令并收到回复
- 插件支持热加载和停用；插件升级或真正卸载在 Windows 上通过重启应用完成
- 第三方开发者可以参照文档和模板开发新的渠道插件

### 12.8 阶段范围边界（Must / Should / Not）

为了避免阶段目标扩散，每个阶段都明确范围边界：

| 阶段 | Must（本阶段必须完成） | Should（有余力可做） | Not（本阶段不做） |
|------|------------------------|----------------------|-------------------|
| 阶段 1 | Identity/Session 模型切换、单视角保持不变、工具权限按 Identity 隔离 | 数据迁移脚本和回滚脚本（如历史格式尚未冻结） | 记忆系统、插件系统 |
| 阶段 2 | 多视角切换、Agent 创建与权限隔离、QTabBar+QStackedWidget 形态、基础性能达标 | 视图性能优化（缓存、懒加载、节流与退化保护） | 群聊协作与跨 Agent 自动委派 |
| 阶段 3 | 私聊/群聊、成员管理、群归档、@机制、消息驱动协作、子 Agent 执行闭环 | 常见协作模板（如代码评审群） | 复杂跨项目编排、全自动长期任务 |
| 阶段 4 | Trace 与调试面板、任务可观测性闭环 | 时间轴回放增强（筛选/检索） | 智能策略优化 |
| 阶段 5 | 记忆沉淀、经验检索、经验复用 | 智能路由策略迭代 | 向量检索重度优化 |
| 阶段 6 | 五大资源库可用、统一访问接口、权限控制 | 语义检索增强、管理界面优化 | 远程多节点共享存储 |
| 阶段 7 | 插件框架、渠道接入、外部消息路由与审计 | 更多参考插件模板 | 无重启插件升级保证 |

### 12.9 跨阶段技术红线（阶段门禁）

以下条目从阶段 1 开始即生效；任一条不满足，则该阶段不得判定“完成”：

1. GUI 主线程不可阻塞：网络、工具调用、子 Agent 执行不得阻塞 UI 事件循环。
2. 统一取消语义：先置任务状态为 `Canceled`，再广播取消，随后中断网络与定时器；取消链路必须幂等并记录 `reason=user_cancel`。
3. 并发预算与限流：至少包含全局、单岗位、单 Provider 三层配额与排队拒绝策略，并产生日志指标。
4. Trace 贯穿：每条用户消息生成 `trace_id` 并透传到任务、工具、日志与审计；阶段 4 完成 UI 聚合与回放能力。
5. 阶段测试门禁：每阶段必须通过最小单测+集成测试；涉及并发/流式改动时需补压力与故障注入用例。

## 十三、不做什么

明确边界，避免方向偏移：

1. **不做通用聊天工具**：TmAgent 不是微信，不支持真人之间的聊天。用户只有一个，其余都是 Agent。
2. **不做 IDE 插件**：TmAgent 是独立的桌面应用，不嵌入 VS Code 或其他 IDE。它通过工具调用（文件操作、LSP、Shell）与开发环境交互。
3. **不做云端 SaaS**：TmAgent 是本地部署的桌面应用，数据存储在本地。不提供多用户、多租户、云端托管等能力。外部通讯渠道是让用户远程控制自己的本地 Agent，而非将 Agent 部署到云端。
4. **不做模型训练/微调平台**：TmAgent 调用现有的 LLM API，不涉及模型训练。
5. **不追求实时性**：Agent 之间的消息传递不需要毫秒级延迟，秒级即可。核心是可靠和可观测，而非速度。
6. **不做移动端**：只做桌面端应用。移动端的需求通过外部通讯渠道插件（微信/飞书/Telegram 等）间接满足。

## 十四、成功标准

当以下场景能够流畅运行时，TmAgent 的核心愿景即已实现：

> 用户打开 TmAgent，创建三个 Agent：架构师、开发者、测试员。
> 用户创建一个群聊"项目重构组"，将三个 Agent 拉入群中。
> 用户在群聊中说："重构 src/core/ 模块，@架构师 先出方案。"
>
> 架构师检索知识库获取项目的设计规范，检索经验库回顾上次重构的经验教训，
> 然后创建子 Agent 分析代码。子 Agent 通过文件库读取源文件、通过 MCP 服务器
> 调用 GitHub 查看相关 Issue，完成分析后汇报结果并销毁。
> 架构师将分析结论内化为经验，在群聊中 @开发者 给出重构方案。
>
> 开发者按照 Skill 库中的"重构标准流程"执行任务，完成后 @测试员 请求验收。
> 测试员运行测试，在群聊中 @用户 报告：全部测试通过，验收完成。
>
> 用户离开办公室后，通过手机上的 Telegram 给 TmAgent 发消息：
> "@架构师 重构的代码有没有性能问题？"
> 架构师基于之前积累的记忆和经验，直接回复分析结论——不需要重新读代码。
>
> 在整个过程中，用户可以随时点击任意 Agent 的 Tab，
> 像登录他们的账号一样，查看他们的会话列表（包括私聊和群聊）、
> 工作进度、子 Agent 执行日志、记忆和经验积累。

## 十五、任务状态机与失败补偿

统一任务状态机，避免不同 Agent/插件各自定义状态导致监控和恢复混乱：

```
Queued -> Running -> Done
           |  \
           |   -> Blocked -> Running
           |
           -> Failed -> Queued（重试）
           -> Canceled
```

规则：
- `Queued`：任务已创建，等待调度
- `Running`：有执行单元（子 Agent/插件）正在处理
- `Blocked`：依赖外部条件（权限确认、外部服务、人工输入）
- `Failed`：执行失败且已记录错误类型，可进入补偿流程
- `Canceled`：用户或系统主动终止，必须保证工具调用和网络请求都被取消

补偿策略：
- 瞬时故障（网络超时、429）：指数退避重试，最多 3 次
- 幂等操作失败：允许自动重放
- 非幂等写操作失败：进入人工确认队列，避免重复执行
- 子 Agent 崩溃：由岗位 Agent 重新创建子 Agent，并附带失败上下文

## 十六、权限模型矩阵

权限默认拒绝，显式授权，最小权限运行：

| 主体 | 读取会话 | 写消息 | 文件写入 | 高风险工具（Shell/Git push） | 跨 Identity 管理 |
|------|----------|--------|----------|-------------------------------|------------------|
| 用户 | 全量 | 全量 | 允许 | 允许（可配置二次确认） | 允许 |
| 岗位 Agent | 仅参与会话 | 允许 | 通过子 Agent 间接执行 | 默认不允许，需任务级授权 | 不允许 |
| 子 Agent | 仅当前任务会话与上下文 | 允许汇报结果 | 按任务沙箱授权 | 按任务显式授权 | 不允许 |
| 插件 | 仅授权范围内 | 仅通过路由器写入 | 默认不允许直接写项目目录 | 不允许 | 不允许 |
| 外部渠道用户 | 仅绑定后的目标会话 | 允许发送指令 | 不允许 | 不允许 | 不允许 |

所有高风险动作必须写入审计日志（操作者、时间、目标、结果、trace_id）。

## 十七、数据生命周期与备份恢复

为保证本地部署下的数据安全与可恢复，定义统一生命周期策略：

| 数据类型 | 在线保留 | 归档策略 | 删除策略 |
|----------|----------|----------|----------|
| Session 消息 | 180 天 | 超期转归档库，支持检索 | 用户手动或策略清理 |
| 工具调用明细 | 30 天 | 保留摘要（输入哈希、结果摘要） | 到期自动清理明细 |
| Trace/监控数据 | 14 天 | 按任务聚合导出 | 自动轮转 |
| 临时文件 | 7 天 | 无 | 任务完成后定期清理 |
| 外部渠道审计日志 | 365 天 | 冷存储压缩归档 | 仅管理员可清理 |

备份与恢复：
- 每日增量备份 `~/.tmagent/`，每周全量快照
- 目标恢复点（RPO）<= 24 小时
- 目标恢复时间（RTO）<= 2 小时
- 恢复流程需要一次校验：数据库可读、索引可用、关键会话可打开
