# TmAgent 愿景落地路线图

> 基于《项目愿景与产品规划》v1.7、《Qt技术约束与前提条件》v1.2、《落地架构讨论报告》v1.1 提炼。
> 日期：2026-02-10
> 状态：active（规范，阶段执行与门禁）

---

## 总览

TmAgent 的愿景是**模拟真人协作方式的多智能体工作台**。从当前的单用户 AI 对话客户端（阶段 0）出发，分 7 步演进到完整愿景。

```
阶段 0（当前）→ 1 → 2 → 3 → 4 → 5 → 6 → 7
  单用户对话    架构  多视角 群聊   可观测 智能化 资源库 插件
  客户端       重塑  Tab   协作   调试   记忆   体系   渠道
```

---

## 阶段 0：当前状态（已完成）

- 单用户视角，扁平会话列表
- 每个会话绑定一个 LLMAgent 实例
- AgentChatWidget 包揽所有逻辑（~1560 行 God Object）
- 会话以行号为主键（QHash<int, ...>），删除时需重索引
- 基础对话 + 工具调用 + 流式输出 + MCP 可用

---

## 阶段 1：架构重塑——引入 Identity-Session 模型

**目标**：功能与当前完全一致，但底层切换为 Identity-Session 数据模型，消除 God Object 和行号主键反模式。  
**阶段边界**：仅完成架构重塑，**暂不引入顶部 Tab 多视角**（保持单用户视角 UI）。

**关键工作**：
1. 定义 Identity、Session、Message、IdentityProfile 数据结构
2. 实现 IdentityManager / SessionManager 管理层
3. 实现 AgentRuntime（每个 Agent 一个实例）+ ChatService（UI 统一入口）
4. AgentChatWidget 瘦身为纯 UI 组件，业务逻辑委托给 Service 层
5. 使用 UUID 替代行号作为会话主键
6. 消息写入统一收口到 `SessionManager::postMessage()`，避免多入口并发写入
7. 去除工具全局共享的隐式耦合，落地按 Identity 隔离的工具权限与运行时边界

**验收标准**：
- 编译通过，所有现有功能正常
- UI 形态保持单视角，不新增顶部 Tab 交互
- AgentChatWidget 不再持有任何 QHash<int, ...>
- 所有业务数据通过 Manager 访问
- Agent 生命周期由 AgentRuntime 管理
- 会话主键全量切换为 UUID，删除会话不再触发行号重排
- 工具权限可按 Identity 生效（至少具备允许/拒绝的校验链路）

**Must**：Identity/Session 模型切换、单视角保持不变、工具权限按 Identity 隔离
**Should**：数据迁移脚本和回滚脚本（如历史格式尚未冻结）
**Not**：记忆系统、插件系统

---

## 阶段 2：多视角——顶部 Tab 切换

**目标**：实现顶部 Tab 栏，用户可以切换到任意 Agent 的视角，查看其会话列表和工作状态。

**关键工作**：
1. 顶部视图切换采用 `QTabBar + QStackedWidget`（不使用 `QTabWidget`）
2. 每个 Tab 对应一个 IdentityView（独立的 ChatListWidget + ChatWidget）
3. Agent 创建流程：用户创建 Agent → 生成 Identity → 新增 Tab
4. Tab 切换时数据源切换到对应 Identity 的 SessionList
5. Agent 视角下的只读/可操作权限控制
6. IdentityView 懒加载与缓存回收策略（避免多 Tab 内存与重绘放大）
7. 多 Tab 流式输出治理：仅可见 Tab 实时渲染，后台 Tab 只更新数据模型

**验收标准**：
- 用户可以创建 Agent，在顶部 Tab 切换视角
- 不同 Tab 显示不同 Identity 的会话列表
- 用户 Tab 固定不可关闭，Agent Tab 可关闭
- Tab 切换延迟目标 <= 200ms（含后台流式刷新场景）
- 后台 Tab 不抢占前台输入体验（输入响应延迟 P95 <= 150ms）

**Must**：多视角切换、Agent 创建与权限隔离、QTabBar+QStackedWidget 形态、基础性能达标
**Should**：视图性能优化（缓存、懒加载、节流与退化保护）
**Not**：群聊协作与跨 Agent 自动委派

---

## 阶段 3：群聊与 Agent 间通信——消息驱动的协作

**目标**：支持私聊和群聊两种 Session 类型，Agent 之间通过消息协作。岗位 Agent 通过子 Agent 执行具体任务。

**关键工作**：
1. 私聊（Private Session）：Agent 主动创建与其他 Agent 的对话
2. 群聊（Group Session）：用户或 Agent 创建群聊，选择多个参与者
3. 群成员管理：owner 可邀请/移除成员，成员可主动退出
4. 群聊归档：任务群完成后归档（保留历史、停止活跃调度）
5. @机制：消息的 mentions 字段指定目标接收者，只有被 @的 Agent 触发决策循环
6. MessageRouter：统一消息路由，群聊广播 + @过滤
7. 子 Agent 执行机制：岗位 Agent 创建子 Agent 执行具体工作，完成后汇报并销毁
8. 结果精炼：岗位 Agent 接收子 Agent 原始结果，提取关键结论
9. ConcurrencyController：并发预算控制

**验收标准**：
- 用户可以创建群聊并邀请多个 Agent
- 群聊中 @某个 Agent 时，只有该 Agent 响应
- Agent 可以自主创建群聊拉入其他 Agent 协作
- 群 owner 的成员管理权限生效（邀请/移除）
- 临时任务群可归档且可追溯历史消息
- 子 Agent 执行闭环（创建 → 执行 → 汇报 → 销毁）

**Must**：私聊/群聊、成员管理、群归档、@机制、消息驱动协作、子 Agent 执行闭环
**Should**：常见协作模板（如代码评审群）
**Not**：复杂跨项目编排、全自动长期任务

---

## 阶段 4：可观测性——调试与监控

**目标**：在 Agent 视角中集成调试面板，支持完整的任务追踪和 Trace 体系。

**关键工作**：
1. Trace 体系落地：每条用户消息生成 trace_id，全链路透传
2. Agent Tab 侧边面板：工具调用日志、任务状态、决策追踪
3. 全局任务视图：跨 Agent 的任务依赖关系和完成状态
4. 时间轴回放：按 trace_id 聚合展示，支持一键回放
5. AgentEventBus 改造：所有信号增加 identityId + traceId

**验收标准**：
- 用户可以在任意 Agent Tab 中查看完整工作轨迹
- 包括工具调用、决策过程、与其他 Agent 的通信记录
- 支持按 trace_id 聚合和回放

**Must**：Trace 与调试面板、任务可观测性闭环
**Should**：时间轴回放增强（筛选/检索）
**Not**：智能策略优化

---

## 阶段 5：智能化——记忆与经验沉淀

**目标**：岗位 Agent 拥有持久记忆，能从历史任务中学习，越用越好。

**关键工作**：
1. 对话记忆（短期）：自动压缩历史对话为摘要
2. 任务记忆（中期）：子 Agent 执行结果摘要存入任务记忆
3. 经验提炼（长期）：从多次任务记忆中提炼稳定结论和方法论
4. 经验检索：岗位 Agent 收到新任务时自动检索相关经验
5. ExperienceManager 落地
6. 智能路由：根据任务类型自动选择最合适的 Agent 和模型组合
7. 渐进式工具授权：按任务阶段动态调整 Agent 的工具权限

**验收标准**：
- 岗位 Agent 能记住之前的对话和任务结果
- 同样的任务第二次执行时，能基于经验做出更好的决策
- 系统能根据历史经验推荐协作方案

**Must**：记忆沉淀、经验检索、经验复用
**Should**：智能路由策略迭代
**Not**：向量检索重度优化

---

## 阶段 6：资源库体系

**目标**：建立五大资源库，为 Agent 提供知识、文件、技能、工具和经验的统一访问能力。

**关键工作**：
1. 知识库（KnowledgeBase）：SQLite + FTS5 全文检索，知识条目增删改查
2. 文件库（FileStore）：文件索引、权限控制、变更通知，与 Git 集成
3. Skill 库（SkillRegistry）：YAML 格式定义，内置 Skill 加载和自定义 Skill 管理
4. MCP 服务器（McpServerRegistry）：注册、健康检查、工具自动发现，兼容主流 MCP Server
5. 经验库（ExperienceStore）：经验条目存储、检索、自动提炼和衰减机制
6. 统一存储：所有资源库数据持久化到 `~/.tmagent/` 目录

**验收标准**：
- 岗位 Agent 收到任务时能自动检索知识库和经验库
- 子 Agent 通过文件库读写文件，权限受控
- 用户可以在设置中管理所有资源库的内容

**Must**：五大资源库可用、统一访问接口、权限控制
**Should**：语义检索增强、管理界面优化
**Not**：远程多节点共享存储

---

## 阶段 7：插件系统与外部通讯渠道

**目标**：实现插件框架，支持通讯渠道插件接入，用户可以通过外部通讯工具远程控制 Agent。

**关键工作**：
1. PluginManager：插件发现、加载、初始化、停用、卸载
2. 插件接口：IChannelPlugin、IExtensionPlugin 等标准接口
3. ChannelManager：统一管理所有通讯渠道插件
4. MessageRouter 扩展：外部消息路由到正确的 Session
5. 身份验证：外部渠道的用户身份验证和权限控制
6. 首个参考渠道插件（如 Telegram Bot）

**验收标准**：
- 用户可以通过外部通讯工具向 Agent 发送指令并收到回复
- 插件支持热加载和停用（真正卸载需重启）
- 第三方开发者可以参照文档和模板开发新的渠道插件

**Must**：插件框架、渠道接入、外部消息路由与审计
**Should**：更多参考插件模板
**Not**：无重启插件升级保证

---

## 阶段依赖关系

```
阶段 1 (架构重塑)
  └─→ 阶段 2 (多视角 Tab)
       └─→ 阶段 3 (群聊协作)
            ├─→ 阶段 4 (可观测性)
            └─→ 阶段 5 (智能化记忆)
                 └─→ 阶段 6 (资源库体系)
                      └─→ 阶段 7 (插件与渠道)
```

阶段 4 和阶段 5 可以并行推进，但都依赖阶段 3 的群聊和子 Agent 机制。

---

## 跨阶段技术红线（阶段门禁）

以下条目从阶段 1 开始即生效；任一条不满足，则该阶段不得判定“完成”。

1. GUI 主线程不可阻塞：网络、工具调用、子 Agent 执行不得阻塞 UI 事件循环。
2. 统一取消语义：先置任务状态为 `Canceled`，再广播取消，随后中断网络与定时器；取消链路必须幂等并记录 `reason=user_cancel`。
3. 并发预算与限流：至少包含全局、单岗位、单 Provider 三层配额与排队拒绝策略，并产生日志指标。
4. Trace 贯穿：每条用户消息生成 `trace_id` 并透传到任务、工具、日志与审计；阶段 4 完成 UI 聚合与回放能力。
5. 阶段测试门禁：每阶段必须通过最小单测+集成测试；涉及并发/流式改动时需补压力与故障注入用例。
