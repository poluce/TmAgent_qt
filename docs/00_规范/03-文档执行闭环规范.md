# TmAgent 文档执行闭环规范

> 状态：active（规范，执行流程闭环）
> 目的：定义“需求进入 -> 方案落地 -> 验收回写 -> 归档治理”的统一流程，避免文档与代码长期漂移。

---

适用于 `docs/` 下所有 active 文档，尤其是：

1. `docs/00_规范/00-项目愿景与产品规划.md`
2. `docs/00_规范/01-Qt技术约束与前提条件.md`

## 二、执行闭环（从哪儿到哪儿）

### 阶段 A：需求进入（入口）

输入来源：

1. 用户反馈/评审意见
2. 线上问题与日志分析
3. 新能力规划（如群聊、记忆、技能）

输出产物：

1. 一个清晰的问题定义（目标、边界、非目标）
2. 一个验收口径草案（用户可感知效果 + 技术验收点）

### 阶段 B：规范对齐（上位约束）

必须先对齐：

1. 愿景边界：`docs/00_规范/00-项目愿景与产品规划.md`
2. 技术硬约束：`docs/00_规范/01-Qt技术约束与前提条件.md`
3. 阶段门禁：`docs/00_规范/02-愿景落地路线图.md`

输出产物：

1. 冲突判断（是否违背规范）
2. 所属阶段定位（归入路线图哪个阶段）

### 阶段 C：方案定义（执行方案）

主执行方案唯一入口：

1. `docs/10_方案/10-架构升级设计方案.md`

专项方案只做补充，不可覆盖主方案与规范：

1. `docs/10_方案/11-记忆系统规划方案.md`
2. `docs/10_方案/12-子模块更新与适配.md`
3. `docs/10_方案/13-tree_sitter_parser_rewrite_plan.md`

输出产物：

1. 实施步骤（按优先级）
2. 风险与回滚策略
3. 验收清单（可测试）
4. 同步更新执行层看板（当前主线/候选池）

### 阶段 D：代码实施（落地）

执行要求：

1. 先改主链路，再补专项细节
2. 同步最小测试与日志可观测点
3. 不做“历史兼容优先”的过度妥协（开发期可直接清理旧路径）

输出产物：

1. 代码变更
2. 测试结果
3. 关键行为说明

### 阶段 E：验收回写（闭环终点）

必须回写到文档：

1. 变更影响到哪个阶段（路线图）
2. 哪些验收点已通过/未通过
3. 当前遗留问题和下一步计划

判定闭环完成的条件：

1. 代码已落地
2. 验收口径可复现
3. 文档已同步
4. 旧描述已清理或归档

### 阶段 F：归档治理（长期维护）

规则：

1. 被替代内容移入 `docs/90_归档/`
2. 归档文档标记 `状态：archived`
3. 在活跃文档中写清“替代关系”

---

## 三、文档合并原则（减少重复）

1. 规范层（00）不合并，保持职责稳定。
2. 方案层（10）允许合并：重复背景与总览应收敛到 `10-架构升级设计方案.md`。
3. 专项方案（11/12/13）只保留“实现差异与操作步骤”，不重复大段背景。
4. 调研层（20）可保留多份原始报告，但应有一份“调研结论汇总”用于快速读取。
5. 任一文档若 60% 以上内容与上位文档重复，必须发起合并或降级为归档。

---

## 四、本项目当前推荐口径

1. 决策顺序：`00 -> 01 -> 02 -> 10 -> 专项`
2. 开发顺序：`10（主线） -> 专项补足 -> 验收回写`
3. 文档变更顺序：`先改规范引用 -> 再改方案内容 -> 最后改归档与索引`
4. 执行入口顺序：`30-当前执行主线 -> 10-架构升级设计方案 -> 代码实施`
