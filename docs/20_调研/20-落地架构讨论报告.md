## 一、现状诊断（三位架构师一致结论）

### 1.1 AgentChatWidget 是 God Object（~1560 行）

同时承担 UI 布局、会话管理、Agent 生命周期、模型配置、MCP 管理、流式状态、持久化等全部职责。

### 1.2 会话以行号为主键——典型反模式

```cpp
QHash<int, LLMAgent*> m_sessionAgents;       // 行号 -> Agent
QHash<int, QJsonArray> m_sessionHistories;    // 行号 -> 历史
QHash<int, QString> m_sessionUuids;           // 行号 -> UUID
QHash<int, StreamState> m_streamStates;       // 行号 -> 流状态
```

删除会话时需要对 5 个 QHash 做行号重索引，是"用 UI 位置做业务主键"的反模式。

### 1.3 全局单例被所有 Agent 共享

`ToolDispatcher::instance()` 和 `ModelFactory::instance()` 被所有 Agent 共享，无法实现按 Identity 隔离工具权限。

### 1.4 AgentTool 使用 QEventLoop 嵌套阻塞

`AgentTool.cpp` 第 106-156 行通过 `QEventLoop::exec()` 同步等待子 Agent，递归深度为 3 时产生 3 层嵌套事件循环，存在重入和取消困难的风险。

### 1.5 Agent 间无法直接通信

当前不存在 Agent 之间的消息传递机制，AgentEventBus 仅转发工具事件（3 个信号），不承担消息路由。

## 二、架构师 A：核心数据模型设计

### 2.1 类层次结构

```
数据模型层 (src/core/model/)
├── Identity : QObject          ← 第一公民，用户和 Agent 统一抽象
│   ├── m_id: QString (UUID)
│   ├── m_type: User | Agent
│   ├── m_profile: IdentityProfile*  (Agent 专属)
│   └── 工厂方法: createUser() / createAgent()
│
├── Session : QObject           ← 共享会话，跨 Identity
│   ├── m_type: Private | Group
│   ├── m_participantIds: QStringList
│   ├── m_messages: QList<Message>
│   └── 信号: messageAdded(), participantAdded()
│
├── Message (值对象/POD struct) ← 不继承 QObject，高效存储
│   ├── senderId, sessionId, mentions
│   ├── content: MessageContent
│   └── 工厂方法: createText() / createToolCall() / createSystem()
│
└── IdentityProfile : QObject   ← Agent 的角色配置
    ├── systemPrompt, modelId, allowedTools
    └── recursionDepth
```

**关键设计决策**：
- **Identity 和 Session 继承 QObject**：利用 parent-child 自动销毁和信号槽机制
- **Message 是值对象（POD struct）**：消息数量可能数千条，每条都创建 QObject 开销过大
- **Session 是共享的**：用户和 Agent 看到的是同一个 Session 指针，不是拷贝

**协作流程**：

```

  → IdentityManager::createAgent(name, profile)
  → SessionManager::createPrivateSession(userId, agentId)
  → UI 更新会话列表

用户发送消息
  → SessionManager::postMessage(sessionId, msg)
  → Session 发射 messageAdded 信号
  → AgentRuntime 监听到消息，触发 LLM 请求
  → LLM 回复后写入 Session → UI 自动更新
```

### 2.7 阶段 1 重构路径（最小改动集）

分 4 步完成，每步保持功能等价：

1. **引入数据模型类**：创建 Identity、Session、Message，纯新增不改现有代码
2. **引入 Manager 层**：创建 IdentityManager、SessionManager，将 AgentChatWidget 中的 QHash 数据迁移
3. **引入 AgentRuntime**：将 LLMAgent 的创建和管理从 AgentChatWidget 移到 AgentRuntime
4. **AgentChatWidget 瘦身**：只保留单视角 UI 布局代码，业务逻辑全部委托给 Service 层（阶段 1 不引入顶部 Tab 多视角）

阶段 1 额外约束：
- 会话主键全量切换为 UUID，删除会话不再做行号重排
- 消息写入统一收口到 `SessionManager::postMessage()` 单入口
- 工具权限按 Identity 生效（至少具备允许/拒绝校验链路）

## 三、架构师 B：通信与协作架构

### 3.1 MessageRouter 设计

MessageRouter 是新架构的核心枢纽，取代当前 AgentChatWidget 中直接调用 Agent 的紧耦合模式：

```cpp
class MessageRouter : public QObject {
    Q_OBJECT
public:
    static MessageRouter* instance();

    // 统一消息入口
    void routeMessage(const Message& message);
    // 外部渠道入口
    void routeExternalMessage(const ChannelMessage& channelMsg);

signals:
    // 消息已投递到 Session（UI 层监听）
    void messageDelivered(const QUuid& sessionId, const Message& message);
    // Agent 需要处理消息（AgentRuntime 监听）
    void agentActivated(const QUuid& agentId, const QUuid& sessionId,
                        const Message& message);
};
```

### 3.2 @机制分发规则

```
消息进入 routeMessage()
│
├── Private Session → 直接激活对方 Agent
│
└── Group Session
    ├── mentionAll == true → 激活所有 Agent 参与者
    ├── mentions 非空 → 只激活被 @的 Agent
    └── mentions 为空 → 不激活任何 Agent（纯上下文记录）

特例：用户发言默认 mentionAll = true
```

**防抢答策略**：多 Agent 同时被 @时，通过 ConcurrencyController 检查并发预算，预算不足时按优先级排队（直接 @ > @all，Session owner 优先）。

### 3.3 群聊广播策略矩阵

| 发送者 | mentions 状态 | Agent 响应行为 |
|--------|-------------|--------------|
| 用户 | 未指定（默认 @all） | 所有 Agent 响应 |
| 用户 | @特定 Agent | 仅被 @的 Agent 响应 |
| Agent | @特定 Agent | 仅被 @的 Agent 响应 |
| Agent | 未 @任何人 | 无 Agent 响应（纯信息发布） |

### 3.4 AgentEventBus 角色重定义

```
新架构事件分层：

┌─────────────────────────────────────────┐
│  业务层：MessageRouter                    │
│  职责：Agent 间消息路由、@机制、群聊广播    │
└──────────────────┬──────────────────────┘
                   │ 使用
┌──────────────────▼──────────────────────┐
│  基础设施层：AgentEventBus               │
│  职责：底层事件传输、可观测性、跨组件解耦  │
│  改造：所有信号增加 identityId + traceId  │
└─────────────────────────────────────────┘
```

AgentEventBus 不再承担消息路由，只负责工具事件、系统事件和 Trace 事件的传输。所有信号增加 `identityId` 和 `traceId` 参数，解决当前全局广播无过滤的问题。

### 3.5 子 Agent 异步化方案

取代当前 `QEventLoop::exec()` 阻塞方案：

```
岗位 Agent 收到任务
  → 创建子 Agent (parent = nullptr, 工作线程中)
  → 子 Agent 异步执行，通过信号上报进度
  → 完成后发射 resultReady 信号
  → 岗位 Agent 在主线程接收结果 (Qt::QueuedConnection)
  → 调用 childAgent->deleteLater()
```

### 3.6 并发控制策略

```
ConcurrencyController
├── 全局子 Agent 并发上限: max(4, CPU核心数), 默认 8
├── 单岗位 Agent 并发上限: 2
├── 单 LLM Provider 并发上限: 按供应商配置, 默认 4
├── 超出预算 → FIFO + 优先级队列
└── 队列超限 → 拒绝并返回可重试错误
```

### 3.7 统一取消语义

```
用户点击"停止"
  → 更新任务状态为 Canceled
  → 向子 Agent 广播取消信号
  → disconnect 网络信号 → abort() QNetworkReply
  → 停止定时器
  → 写入统一结束事件 (reason=user_cancel)

所有取消路径幂等（重复取消不崩溃不重复回调）
```

### 4.2 QChatWidget 改造：适配层方案

**不直接修改 QChatWidget 子模块**，通过适配层桥接：

```
Session (核心模型)                    ChatWidgetModel (UI 模型)
    │                                      ▲
    │ 信号: messageAdded                    │ 调用: addMessage()
    ▼                                      │
SessionDataBridge (适配层)  ──────────────→ │
    - Message → ChatWidgetMessage 转换
    - senderId → displayName 映射
    - 流式增量更新处理
    - @mention UUID → 显示名称转换

SessionManager                        ChatListWidget
    │                                      ▲
    │ 信号: sessionCreated                  │ 调用: addChatItem()
    ▼                                      │
SessionListBridge (适配层) ──────────────→ │
    - 按 Identity 过滤会话
    - Session → ChatListItem 转换
```

这样 QChatWidget 子模块保持独立纯净，所有 Identity-Session 业务逻辑在 Bridge 层处理。

### 4.3 @mention 高亮

已有基础设施：
- `ChatWidgetMessage` 已有 `mentions` 字段
- `ChatWidgetDelegate::Style` 已有 `mentionHighlightColor = QColor(255, 233, 198)`

### 4.4 多 Tab 流式输出性能优化

| 策略 | 说明 |
|------|------|
| 可见 Tab 实时渲染 | 后台 Tab 只更新数据模型，不触发 UI 重绘 |
| Markdown 缓存 | 流式完成后缓存 QStaticText，避免重复渲染 |
| 节流 33ms | delta 到达频率过高时限制 UI 更新到 30 FPS |
| 退化保护 | 主线程延迟 > 150ms 时自动降级（纯文本、降采样） |

**性能基线目标**：

| 场景 | 指标 | 目标值 |
|------|------|--------|
| 5 个并行流式输出 | UI 主线程帧率 | >= 30 FPS |
| 10 个并行流式输出 | 输入响应延迟 P95 | <= 150 ms |
| 2 小时持续运行 | 内存增长 | <= 20% |
| Tab 切换（含后台流式数据刷新） | 切换延迟 | <= 200 ms |

## 五、三位架构师共识的风险点

| 风险 | 严重度 | 缓解措施 |
|------|--------|---------|
| QEventLoop 嵌套（约束 3） | **高** | 阶段 1 限制递归 ≤ 2 + 超时保护；阶段 3 改用异步状态机 |
| AgentChatWidget 重构范围大 | **高** | 分 4 步渐进重构，每步保持功能等价 |
| 多 Agent 并行时 QNetworkAccessManager 线程亲和性 | **中** | 阶段 1-2 主线程共享实例；阶段 3+ 每工作线程独立实例 |
| 插件 ABI 兼容性（约束 11） | **中** | 严格锁定编译环境，提供插件 SDK 和编译模板 |
| Session 共享的并发写入 | **中** | 所有消息写入通过 SessionManager::postMessage() 单入口序列化 |
| 行号索引迁移到 UUID 索引 | **低** | 阶段 1 一次性完成，有回滚脚本 |

### 步骤 4：AgentChatWidget 瘦身（单视角）

- AgentChatWidget 瘦身为纯 UI 组件（保持单视角）
- 业务逻辑委托给 Service 层
- 不引入顶部 Tab 多视角交互

### 验收标准

- 功能与当前完全一致，但底层已切换为 Identity-Session 模型
- UI 形态保持单视角，不新增顶部 Tab 交互
- 会话主键为 UUID，删除会话不再触发行号重排
- 工具权限按 Identity 生效

### 阶段 2：多视角补充（顶部 Tab）

- 顶部视图切换采用 **QTabBar + QStackedWidget**（不使用 QTabWidget）
- `IdentityView` 按需懒加载，超限回收
- 多 Tab 流式场景下：可见 Tab 实时渲染，后台 Tab 仅更新数据模型
- 性能目标：Tab 切换延迟 <= 200ms；输入响应延迟 P95 <= 150ms

### 阶段 3：协作补充（群聊）

- 支持群成员管理：owner 邀请/移除成员，成员可主动退出
- 支持任务群归档：完成后归档，保留历史、停止活跃调度
- 并发预算由 ConcurrencyController 控制（全局/单岗位/单 Provider）

## 七、跨阶段技术红线（阶段门禁）

以下条目从阶段 1 开始即生效；任一条不满足，则该阶段不得判定“完成”：

1. GUI 主线程不可阻塞：网络、工具调用、子 Agent 执行不得阻塞 UI 事件循环。
2. 统一取消语义：先置任务状态为 `Canceled`，再广播取消，随后中断网络与定时器；取消链路必须幂等并记录 `reason=user_cancel`。
3. 并发预算与限流：至少包含全局、单岗位、单 Provider 三层配额与排队拒绝策略，并产生日志指标。
4. Trace 贯穿：每条用户消息生成 `trace_id` 并透传到任务、工具、日志与审计；阶段 4 完成 UI 聚合与回放能力。
5. 阶段测试门禁：每阶段必须通过最小单测+集成测试；涉及并发/流式改动时需补压力与故障注入用例。
