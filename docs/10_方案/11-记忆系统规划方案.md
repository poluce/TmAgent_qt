# TmAgent 记忆系统规划方案（实施细则）

> 状态：active（专项方案）
> 角色：阶段 5「智能化记忆」的实施细则；当前执行策略为阶段 3A 前置落地 M1 基础闭环。
> 上位约束：`docs/10_方案/10-架构升级设计方案.md`、`docs/00_规范/03-文档执行闭环规范.md`

---

## 一、文档定位

本文件只回答三件事：

1. 记忆数据存什么。
2. 记忆数据如何在运行时读写。
3. 阶段 5 如何按里程碑落地并验收。

不在本文件重复：

1. ChatService 全局拆分方案。
2. 多 Agent 协作总体架构。
3. 调研原文分析过程。

---

## 二、统一口径（必须遵守）

### 2.1 单一事实源

1. Markdown 记忆文件是记忆主真源（source of truth）。
2. JSONL 事件日志是执行与审计真源。
3. SQLite/FTS/向量索引是派生索引，可重建，不是主真源。

### 2.2 读写边界

1. 会话历史（Session/Message）与记忆文档分离存储。
2. 删除会话不删除 Agent 记忆文档。
3. 删除 Agent 时，连带删除其身份目录与记忆目录。

### 2.3 组装边界

1. 记忆注入在 Service 层请求组装阶段完成。
2. 不在 LLMAgent 内维护额外可变记忆状态，避免“双轨上下文”。

## 三、目标目录与文件模型

### 3.1 目录模型

```text
~/.tmagent/
  user.md
  shared_work.md
  config/
    memory_policy.json
  identities/
    agents/
      {agentId}/
        profile.json
        soul.md
        identity.md
        memory.md
        user_view.md
        memory/
          YYYY-MM-DD.md
```

### 3.2 文件职责

1. `soul.md`：人格准则和边界。
2. `identity.md`：身份卡（名称、岗位、性格、模型偏好、头像）。
3. `user.md`：用户公共画像和长期偏好（所有助手共享）。
4. `shared_work.md`：公共近期工作记忆（由记忆管家助手维护）。
5. `user_view.md`：某个助手对用户的私有印象记忆（每个助手独立）。
6. `memory.md`：该助手提炼后的长期记忆。
7. `memory/YYYY-MM-DD.md`：该助手每日原始记忆日志。
8. `config/memory_policy.json`：记忆策略（如 `memory_steward_agent_id`）。
9. `config/memory_policy.json` 的 `memory_rules`：
   - `auto_extract_enabled`：是否自动提炼长期记忆。
   - `min_user_chars_for_extract`：自动提炼的最小用户输入长度门槛。
   - `max_long_memory_candidates_per_turn`：每回合长期记忆候选写入上限。

### 3.3 内容要求

1. 文档可读、可人工编辑。
2. 写入采用原子策略（tmp + rename）。
3. 每条提炼记忆可追溯到 `session_id/turn_id/trace_id`。

### 3.4 配置入口（记忆页）

1. 在主界面提供独立“记忆”配置页。
2. 用户可选择“记忆管家助手”及其模型（写入 `config/memory_policy.json` + 对应 Agent `profile.json`）。
3. 用户可填写/修改公共画像字段（写入 `user.md`）。
4. 用户可不填写字段，系统保留空值并继续运行。
5. 用户仍可直接手动编辑 `user.md`；UI 负责读取并回显。

## 四、运行时闭环（Retain / Recall / Reflect）

### 4.1 Recall（注入）

触发时机：`ChatService::tryStartNextTurn()`。

流程：

1. 读取 `soul.md`、`identity.md`、`user.md`、`shared_work.md`、`user_view.md`、`memory.md`。
2. 读取最近两天 `daily` 日志摘要。
3. 按预算裁剪（token/字符上限）。
4. 作为 system 上下文的一部分注入本轮请求。

### 4.2 Retain（留存）

触发时机：`ChatService::onRuntimeFinished()`。

流程：

1. 从本轮消息提取候选记忆（规则优先，LLM 提取可后置）。
2. 追加写入当日日志 `memory/YYYY-MM-DD.md`（助手私有）。
3. 追加写入 `user_view.md`（助手私有用户印象）。
4. 当且仅当当前助手是记忆管家（`memory_steward_agent_id`）时，追加写入 `shared_work.md`。
5. 对符合长期条件的条目写入 `memory.md`。
6. 发出 `memory.updated` 事件供 UI 和日志使用。

### 4.3 Reflect（反思）

触发策略：按条数或按日批处理。

流程：

1. 对近期 `daily` 日志做去重和合并。
2. 将稳定事实上升到 `memory.md`。
3. 对过期临时信息做降级或清理。

## 五、代码接口契约（最小集）

### 5.1 MemoryManager

职责：统一记忆读写、组装、提取调度。

最小接口：

1. `initializeForAgent(agentId, profile)`
2. `composeMemoryContext(agentId)`
3. `extractFromTurn(agentId, sessionId, turnMessages, traceId)`
4. `removeAgentMemory(agentId)`

### 5.2 MemoryDocument

职责：单文档读写封装。

最小能力：

1. `read()`
2. `writeAtomic(content)`
3. `appendAtomic(entry)`
4. `readTruncated(maxChars)`

### 5.3 事件契约

统一事件类型：

1. `memory.updated`
2. `memory.compacted`
3. `memory.error`

统一最小字段：

1. `identity_id`
2. `session_id`
3. `turn_id`
4. `trace_id`
5. `doc_type`
6. `summary`

## 六、实施里程碑

### 6.0 与主线阶段对齐（1-7）

1. 阶段 1-2：不落记忆功能，仅保留记忆边界与数据模型约束。
2. 阶段 3：先完成 M1 基础闭环，不提前引入 FTS/向量能力。
3. 阶段 4：补齐 M1 的可观测性闭环（事件、trace 追踪、排障）。
4. 阶段 5：完成 M2（长期提炼与去重），形成“可持续沉淀”。
5. 阶段 6：完成 M3（FTS 派生索引与检索能力）。
6. 阶段 7：完成 M4（混合检索与质量评分），插件通过统一接口消费。

### M1（当前优先）

目标：基础读写与注入闭环。

交付：

1. 初始化文档生成。
2. 回合前注入。
3. 回合后 daily 追加。
4. 原子写与错误日志。
5. 记忆配置页（记忆管家/模型/用户画像）落地。

### M2

目标：长期记忆提炼与去重。

交付：

1. `memory.md` 提炼策略。
2. 重复检测规则。
3. 手动“记住这条”入口。

### M3

目标：检索能力。

交付：

1. SQLite FTS5 派生索引。
2. `memory_search` 工具。
3. 索引损坏重建流程。

### M4

目标：高级反思与混合检索。

交付：

1. 向量检索接入。
2. BM25 + 向量混合排序。
3. 记忆质量评分与定期反思任务。

## 七、验收标准

### 7.1 功能验收

1. 应用重启后，Agent 能恢复同一套记忆行为。
2. 用户说“记住 X”后，能在 `memory.md` 或当日日志看到可追溯条目。
3. 删除会话不丢记忆，删除 Agent 才删除其记忆目录。

### 7.2 工程验收

1. 不引入新的双轨历史。
2. 注入和提取不阻塞 GUI 主线程。
3. 索引可重建且不破坏 Markdown 主真源。

### 7.3 观测验收

1. 可用 `trace_id` 追踪一次“提问 -> 提取 -> 写入”的完整链路。
2. 记忆错误有结构化日志，不只弹窗文本。

### 7.4 阶段门禁补充（防止越阶段实现）

1. 阶段 3/4 不得把 FTS5 或向量索引作为记忆主链路依赖。
2. 阶段 5 验收前，不得把“长期提炼正确性”标记为已完成。
3. 阶段 6/7 的检索能力失败，不得破坏 Markdown 真源读写与回放。

## 八、风险与控制

1. 上下文过大：注入预算 + 分段裁剪。
2. 低质量记忆污染：规则门槛 + 反思去重。
3. 并发写冲突：按 Agent 目录隔离 + 原子写。
4. 文档漂移：每次迭代必须回写本文件与主方案的阶段状态。
