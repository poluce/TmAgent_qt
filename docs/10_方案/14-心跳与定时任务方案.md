## 二、三层心跳模型

TmAgent 的心跳不是单一机制，而是三层分离、各司其职：

```
全局唯一                       每 Agent 独立
    │                       ┌──────┴──────┐
第1层 HealthMonitor       第2层 HeartbeatSvc   第3层 AgentPulse
 基础设施存活监控          主动唤醒心跳          状态心跳
 LLM/MCP/LSP 探活        HEARTBEAT.md 驱动     卡死/超时/停滞检测
 5-30s 轻量 ping          30min-2h LLM 调用     1-30s 状态上报
```

### 2.1 第 1 层：HealthMonitor（全局基础设施监控）

- 监控 LLM Provider API 可达性、MCP Server 连接、LSP 进程存活。
- 全局唯一实例，所有 Agent 共享探测结果。
- 异常时通过 AgentEventBus 广播，受影响的 Agent 自行降级。

### 2.2 第 2 层：HeartbeatService（Agent 主动唤醒）

- 每个 Agent 按自己的节奏"醒来"做后台工作（记忆整理、主动关怀、项目巡检）。
- 每个 Agent 配置不同：助理 Agent 可能 30 分钟一次，监控 Agent 可能 5 分钟一次。
- 触发 LLM 调用，由 LLM 自主决定是否通知用户。

### 2.3 第 3 层：AgentPulse（Agent 状态心跳）

- 每个 Agent 的健康状态检测：是否卡死、回合是否超时、工具循环是否死锁。
- 其他 Agent 或用户可以感知某个 Agent "还活着吗"。
- 当前 `DelegateTaskScheduler` 的 watchdog（1s 间隔 + 软超时 + 硬超时 + 停滞检测）是第 3 层的雏形。

### 2.4 三层联动关系

三层不是孤立的，基础设施状态会向上影响：

| 全局事件 | 对 AgentPulse 的影响 | 对 HeartbeatService 的影响 |
|---------|---------------------|--------------------------|
| Provider 不可达 | 状态标记为 `degraded` | 暂停唤醒（调 LLM 也会失败） |
| Provider 恢复 | 状态恢复 `healthy` | 恢复唤醒调度 |
| MCP 断连 | 工具能力降级 | 唤醒时跳过依赖该工具的任务 |
| LSP 崩溃 | 代码能力降级 | 不影响（唤醒不依赖 LSP） |

## 三、心跳与子代理委派的交互

### 3.1 三层心跳对子代理的意义

| 心跳层 | 对子代理有意义吗 | 原因 |
|--------|----------------|------|
| HealthMonitor | 有（被动受益） | 子代理依赖 Provider/MCP，基础设施挂了可提前感知 |
| HeartbeatService | 无 | 子代理是纯任务执行者，没有"内在生活" |
| AgentPulse | 最关键 | 检测子代理卡死/停滞，现有 watchdog 已覆盖 |

核心原则：**不为子代理注册 HeartbeatService**，子代理的监控完全由 AgentPulse（watchdog）负责。

### 3.2 委派期间的心跳策略——暂停主动唤醒，保持被动感知

主代理委派子代理后，三层心跳的行为：

```
主代理委派了子代理去干活
  │
  ├─ 子代理还活着吗？        → AgentPulse（第3层）持续监控，1s 一次
  ├─ Provider 还能用吗？     → HealthMonitor（第1层）持续监控
  └─ 主代理需要"醒来"做事吗？ → HeartbeatService（第2层）暂停主动唤醒
```

暂停第 2 层的原因：主代理正在等待工具结果，此时触发新的 LLM 调用会导致状态冲突（QEventLoop 嵌套重入）。但感知能力不中断——第 1 层和第 3 层始终在线。

委派完成后，HeartbeatService 自动恢复，并在距上次心跳已超过间隔时补触发一次。

### 3.3 子代理卡死时的协作链路

```
AgentPulse 检测到子代理停滞（第3层）
  │
  ├─ HealthMonitor 判断是否是基础设施问题（第1层）
  │   ├─ 是 → 标记 failureReason = "provider_unavailable"
  │   └─ 否 → 标记 failureReason = "stalled"
  │
  ├─ 软超时 → 通知主代理，主代理可决定等待或重试
  └─ 硬超时 → 强制终止子代理，结果返回主代理
       │
       └─ 主代理下次心跳时（第2层恢复后）可主动向用户汇报

```

### 3.4 多层委派（A → B → C）

心跳不传播，只在顶层管理：
- 每层子代理有独立的 watchdog（AgentPulse），由 DelegateTaskScheduler 管理。
- HeartbeatService 只注册给岗位 Agent（顶层），子代理不注册。
- 递归深度由 `LLMConfig::recursionDepth` 控制（默认 2-3 层）。

## 四、需求分析

### 4.1 为什么需要心跳

当前 TmAgent 的 Agent 是完全被动的——只有用户发消息才会触发响应。缺少：

1. **主动关怀**：Agent 无法主动联系用户（如晨间问候、定期签到）。
2. **后台维护**：记忆整理、文档更新等维护任务无法自动执行。
3. **健康监控**：无法感知 MCP 服务器、LSP 进程等外部依赖的存活状态。

### 4.2 为什么需要定时任务

心跳是粗粒度的周期性唤醒，但某些场景需要精确调度：

1. **精准时间点**：每天 9:00 晨间简报、每周一复盘。
2. **会话隔离**：定时任务应在独立会话中执行，不污染主对话。
3. **一次性提醒**：20 分钟后提醒我某件事。

### 4.3 与现有系统的关系

| 现有能力 | 心跳/定时任务的补充 |
|---------|-------------------|
| 记忆系统（M1-M4） | 心跳触发记忆整理/反思，定时任务触发记忆备份 |
| AgentEventBus | 心跳/任务事件接入统一事件流 |
| 工具循环熔断 | 心跳触发的 LLM 调用复用现有熔断策略 |
| 子代理委派 | 定时任务可委派给子代理执行 |
| MessageRouter | 群聊就绪后，心跳消息可路由到群聊 |

```
│  │HealthMonitor │  │HeartbeatSvc   │  │SchedulerSvc   │  │
│  │(第1层·全局)   │  │(第2层·每Agent) │  │(精准调度)      │  │
│  └──────┬───────┘  └──────┬────────┘  └──────┬────────┘  │
│         │                  │                   │           │
│         │           ┌──────┴────────┐          │           │
│         │           │ HeartbeatWake │          │           │
│         │           │ 250ms合并窗口  │          │           │
│         │           └──────┬────────┘          │           │
│         │                  │                   │           │
│         ▼                  ▼                   ▼           │
│  ┌─────────────────────────────────────────────────────┐  │
│  │              AgentRuntime / LLMAgent                 │  │
│  │  ┌───────────┐                                      │  │
│  │  │AgentPulse │  ← 第3层·每Agent实例，含子代理watchdog │  │
│  │  └───────────┘                                      │  │
│  └─────────────────────────────────────────────────────┘  │
└──────────────────────────┬───────────────────────────────┘
                           │
                           ▼
                     AgentEventBus
          (infra.* / heartbeat.* / pulse.* / scheduler.*)
```

信号槽连接拓扑：

```
HealthMonitor
  └─→ AgentEventBus::infraStateChanged
        ├─→ DelegateTaskScheduler（检查受影响的子代理）
        ├─→ HeartbeatService（Provider 不可用时暂停唤醒）
        └─→ UI（状态栏显示基础设施状态）

AgentPulse
  └─→ stateChanged / hardTimeoutReached
        ├─→ DelegateTaskScheduler::settleAsyncJob（子代理超时）
        └─→ ChatService（主代理卡死告警）

HeartbeatService
  └─→ heartbeatTriggered
        └─→ ChatService::onHeartbeatTriggered
              ├─→ 读取 HEARTBEAT.md
              ├─→ 查询 DelegateTaskScheduler 后台任务状态
              └─→ 调用 AgentRuntime::handleHeartbeat
```

### 5.3 AgentPulse — Agent 状态心跳（第 3 层）

职责：每个 Agent 实例一个，检测 Agent 是否卡死/停滞。对子代理复用现有 watchdog 逻辑。

```cpp

    Q_OBJECT
public:
    explicit AgentPulse(const QString &agentId, QObject *parent = nullptr);

    void start(int intervalMs = 1000);
    void stop();

    void reportProgress(const QString &summary = QString());

    enum State { Healthy, SoftTimeout, Stalled, HardTimeout, Dead };
    State currentState() const;
    qint64 idleMs() const;

signals:
    void stateChanged(const QString &agentId, AgentPulse::State newState);
    void hardTimeoutReached(const QString &agentId);

private:
    void onTick();

    QString m_agentId;
    QTimer *m_timer = nullptr;

```

与 DelegateTaskScheduler watchdog 的分工：

| 维度 | watchdog (DelegateTaskScheduler) | AgentPulse |
|------|--------------------------------|------------|
| 粒度 | 单个子代理任务 | 主代理整体 |
| 间隔 | 1s | 1-30s |
| 职责 | 超时中断、stall 检测 | 健康状态聚合、UI 展示 |
| 动作 | abort 子代理 | 通知 UI、触发告警 |

## 六、与现有系统的集成

### 6.1 与 AgentRuntime 集成

心跳触发时，通过 ChatService 调用 AgentRuntime 的 LLM 链路：

```cpp
// ChatService 中的心跳处理
void ChatService::onHeartbeatTriggered(const QString &agentId, const QString &reason) {
    auto *runtime = m_runtimes.value(agentId);
    if (!runtime) {
        runtime = ensureRuntimeForAgent(agentId);
    }

    // 读取 HEARTBEAT.md 内容
    QString content = MemoryManager::instance().readHeartbeatContent(agentId);
    if (content.trimmed().isEmpty() && reason != "exec") {
        emit AgentEventBus::instance().heartbeatSkipped(agentId, "empty-content");
        return;
    }

    // 构造心跳消息，注入主会话
    runtime->handleHeartbeat(content, reason);
}
```

### 6.3 与记忆系统集成

心跳是记忆反思的天然触发点：

1. 心跳回调中可调用 `MemoryManager::reflectIfNeeded()` 触发记忆整理。
2. HEARTBEAT.md 中可配置"检查记忆健康度"作为心跳任务之一。
3. 定时任务可配置"每日记忆备份"。

### 6.4 与并发控制集成

复用现有的工具循环熔断策略：

1. 心跳触发的 LLM 调用受 `tool_loop_policy.json` 约束。
2. 如果用户正在对话（有活跃回合），心跳排队等待（HeartbeatWake 的 running 标志）。
3. 定时任务的 `sessionTarget: "isolated"` 在独立会话中执行，不阻塞主会话。

### 6.5 活跃时间窗口检查

```cpp
bool HeartbeatService::isInActiveHours(const ActiveHours &hours) const {
    if (hours.start.isNull() || hours.end.isNull()) {
        return true;  // 未配置则始终活跃
    }

    QDateTime now = QDateTime::currentDateTime();
    if (!hours.timezone.isEmpty()) {
        now = now.toTimeZone(QTimeZone(hours.timezone.toUtf8()));
    }

    QTime currentTime = now.time();

    if (hours.start <= hours.end) {
        // 不跨午夜：08:00 - 23:00
        return currentTime >= hours.start && currentTime <= hours.end;
    } else {
        // 跨午夜：22:00 - 06:00
        return currentTime >= hours.start || currentTime <= hours.end;
    }
}
```

### 6.6 与 DelegateTaskScheduler 集成

```cpp

HeartbeatService::instance().suppressHeartbeat(ownerAgentId, "delegate_in_progress");

// DelegateTaskScheduler::settleAsyncJob 中：
// 委派完成后恢复主动唤醒（内部自动判断是否需要补触发）
HeartbeatService::instance().unsuppressHeartbeat(runtime->ownerAgentId);
```

心跳回调中注入后台任务上下文（异步委派模式）：

```cpp
void ChatService::onHeartbeatTriggered(const QString &agentId, const QString &reason) {
    // ... 现有心跳逻辑 ...

    // 检查该 Agent 是否有未完成的后台委派任务
    const auto activeJobs =
        DelegateTaskScheduler::instance()->listJobs(agentId, true, 5);

    if (!activeJobs.isEmpty()) {
        QString jobContext;
        for (const auto &job : activeJobs) {
            jobContext += QString("- 后台任务 %1: %2 (%3)\n")
                .arg(job.jobId, job.summary, job.status);
        }
        content += "\n\n[后台任务状态]\n" + jobContext;
    }
}
```

HealthMonitor 检测到 Provider 不可用时，中断受影响的子代理：

```cpp
void ChatService::onProviderDown(const QString &configId, const QString &reason) {
    // 1. 中断所有使用该 Provider 的活跃 Runtime
    for (auto it = m_runtimes.begin(); it != m_runtimes.end(); ++it) {
        AgentRuntime *runtime = it.value();
        if (runtime->currentConfigId() == configId) {
            runtime->agent()->abort();
        }
    }

    // 2. 中断所有使用该 Provider 的异步子代理任务
    auto *scheduler = DelegateTaskScheduler::instance();
    const auto activeJobs = scheduler->listJobs(QString(), true, 200);
    for (const auto &job : activeJobs) {
        if (job.childConfigId == configId) {
            QString error;
            scheduler->cancelJob(job.jobId, QString(), &error);
        }
    }

    // 3. 通知 UI
    AgentEventBus::instance()->postLog(
        QString("Provider %1 不可用: %2").arg(configId, reason), "error");
}
```

注意：`onProviderDown` 通过 `Qt::QueuedConnection` 连接，确保在主线程执行。

## 八、里程碑规划

### H0：基础设施监控与状态心跳

目标：第 1 层 HealthMonitor 和第 3 层 AgentPulse 可用。

工作项：
1. 实现 `HealthMonitor` 全局单例（Provider/MCP/LSP 探活）
2. 实现 `AgentPulse` 状态心跳（复用现有 watchdog 逻辑抽象）
3. HealthMonitor → AgentEventBus 事件接入
4. AgentPulse → DelegateTaskScheduler 联动（子代理卡死检测）
5. HealthMonitor 检测到 Provider 不可用时中断受影响的子代理
6. UI 状态栏显示基础设施健康状态

验收标准：
- Provider 不可达时 5s 内检测到并广播事件
- 子代理卡死时 AgentPulse 触发 stateChanged 信号
- Provider 恢复后自动恢复状态
- UI 状态栏实时反映基础设施状态

### H1：心跳基础闭环

目标：单个 Agent 的心跳周期唤醒可用。

工作项：
1. 实现 `HeartbeatConfig` 数据模型与 JSON 持久化
2. 实现 `HeartbeatWake` 请求合并器（QTimer + 状态机）
3. 实现 `HeartbeatService` 核心调度逻辑
4. 实现 `suppressHeartbeat` / `unsuppressHeartbeat`（委派期间暂停主动唤醒）
5. ChatService 接入心跳触发 → AgentRuntime LLM 调用
6. DelegateTaskScheduler 集成（委派开始暂停、完成恢复、补触发）
7. HEARTBEAT.md 读取与空内容检测
8. 活跃时间窗口检查
9. AgentEventBus 接入心跳事件
10. 心跳配置 UI（信息设置页扩展）

验收标准：
- Agent 启用心跳后，按配置间隔自动触发 LLM 调用
- 活跃时间窗口外不触发
- HEARTBEAT.md 为空时跳过（exec 豁免）
- 委派子代理期间心跳自动暂停，委派完成后自动恢复
- 委派完成后若距上次心跳已超过间隔，自动补触发一次
- 心跳事件在右侧面板可见
- 用户对话期间心跳不中断对话

### H2：心跳增强

目标：重复抑制、手动触发、热加载。

工作项：
1. 重复消息抑制（24h 窗口 + 文本比较）
2. 手动触发入口（UI 按钮 + 工具命令）
3. 配置热加载（修改间隔/活跃时间即时生效）
4. 心跳状态持久化（`heartbeat_state.json`）
5. 心跳与记忆反思联动（心跳时触发 `reflectIfNeeded`）

验收标准：
- 24h 内相同回复不重复发送
- UI 修改心跳配置后无需重启即生效
- 应用重启后心跳状态恢复（不会立即重复触发）

### H3：定时任务基础

目标：Cron 定时任务可用。

工作项：
1. 实现 `CronParser`（5 段 cron 表达式解析）
2. 实现 `ScheduledJob` / `JobRun` 数据模型
3. 实现 `SchedulerService` 核心调度逻辑
4. 任务持久化（`scheduled_jobs.json` + `job_runs/*.jsonl`）
5. ChatService 接入定时任务触发
6. AgentEventBus 接入调度事件
7. 定时任务管理 UI

验收标准：
- 可创建 Cron 定时任务并按时触发
- 任务执行历史可查
- 任务支持启用/禁用/手动触发
- 应用重启后任务自动恢复调度

### H4：定时任务增强

目标：会话隔离、一次性任务、与群聊联动。

工作项：

2. 一次性任务支持（执行后自动禁用）
3. `agentTurn` payload 类型支持
4. 与群聊 MessageRouter 联动（群聊就绪后）
5. 任务模板（晨间简报、每日复盘等预设）

验收标准：
- isolated 任务在独立会话中执行，不影响主对话
- 一次性任务执行后自动标记为已完成
- 预设模板可一键创建

## 九、与路线图的关系

心跳与定时任务是**跨阶段能力**，不属于路线图中的单一阶段：

| 里程碑 | 依赖的路线图阶段 | 说明 |
|--------|-----------------|------|
| H0 | 当前即可启动 | 仅依赖现有 AgentRuntime + DelegateTaskScheduler |
| H1 | 当前即可启动 | 仅依赖 AgentRuntime + ChatService，已就绪 |
| H2 | 当前即可启动 | 依赖记忆系统（M4 已就绪） |
| H3 | 当前即可启动 | 独立能力，不依赖群聊 |
| H4 | 部分依赖阶段 3（群聊） | isolated session 可先行，群聊联动后置 |

建议执行策略：H0 → H1 → H2 → H3 → H4，H0 与 H1 可并行推进，与当前 M4 收口和群聊准备同步进行。

## 十、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 心跳阻塞主线程 | UI 卡顿 | 心跳 LLM 调用复用现有异步链路，不引入同步等待 |
| 心跳与用户对话冲突 | 消息交错 | HeartbeatWake 的 running 标志 + 活跃回合检测 |
| Cron 解析复杂度 | 引入 bug | 优先使用成熟的 croncpp 库，或限制为简单子集 |
| 定时任务堆积 | 资源耗尽 | 全局并发预算控制，同一 Agent 同时只执行一个定时任务 |
| 应用未运行时错过任务 | 任务丢失 | 启动时检查 missed jobs，可选补执行 |
| 委派期间心跳暂停过久 | 主代理"失联" | unsuppress 后自动补触发 + 硬超时兜底 |
| Provider 不可达未及时检测 | 子代理空转 | HealthMonitor 5s 探活 + 失败快速中断 |
| QEventLoop 嵌套重入 | 状态混乱 | 委派期间严格暂停第 2 层，不允许新 LLM 调用 |

## 十一、技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 心跳定时器 | `QTimer::singleShot` | 精确计算下次时间，避免 setInterval 漂移 |
| 请求合并 | 自实现 HeartbeatWake | 逻辑简单，无需引入外部库 |
| Cron 解析 | croncpp（header-only）或自实现 | 轻量，MIT 许可，无额外依赖 |
| 任务持久化 | JSON + JSONL | 与现有持久化方案一致（Markdown + JSONL） |
| 事件总线 | AgentEventBus 扩展 | 复用现有基础设施 |
| 并发控制 | 现有工具循环熔断 | 不引入新的并发机制 |
