# TmAgent 心跳与定时任务方案

> 状态：active（按 2026-03-25 当前实现同步）
> 角色：后台巡检、主动维护与精准调度的实现说明
> 关联代码：`src/core/service/include/HeartbeatService.h`、`src/core/service/include/HeartbeatTypes.h`、`src/core/service/include/HeartbeatStateStore.h`
> 说明：`docs/20_调研/*` 中的上游实现术语仅作为调研参考，不代表当前落地实现

---

## 一、定位

当前实现把“心跳”定义为：

**一个规则优先的后台巡检引擎。**

它负责按节奏采样状态、执行维护、按需升级到 LLM，并只在关键变化时向主会话投递摘要。

与 `SchedulerService` 的边界如下：

| 机制 | 解决问题 | 执行通道 | 时间语义 | 用户可见性 |
|------|----------|----------|----------|------------|
| Heartbeat | 后台巡检、主动维护、风险感知、恢复补跑 | 独立后台 lane | 粗粒度 cadence + 事件驱动 | 默认静默，仅关键变化投递摘要 |
| Scheduler | 精确到点任务（Cron） | 正常任务调度链路 | 精确触发 | 可直接面向业务提醒 |

结论：

1. 心跳不是网络保活，也不是精确调度器。
2. 心跳不再复用主会话 turn 队列。
3. 心跳只在“需要同步给用户”时把最终摘要投递回主会话。

## 二、当前实现模型

### 2.1 总体结构

```text
HeartbeatService
  ├─ HeartbeatSnapshotService
  ├─ HeartbeatDecisionEngine
  ├─ HeartbeatExecutionService
  │    ├─ maintenance
  │    └─ escalation (optional)
  └─ HeartbeatStateStore
```

### 2.2 核心原则

1. **规则优先**：先采样、判定、维护，再决定是否升级到 LLM。
2. **独立后台 lane**：每个 Agent 只有 1 条后台心跳 lane，串行执行。
3. **默认静默**：自动心跳不直接刷消息；只有关键变化才产出摘要。
4. **补充指令降级**：`HEARTBEAT.md` 只在升级阶段参与 prompt，不再决定调度或静默语义。
5. **重启可恢复**：恢复 pending/deferred/recovery 状态；错过窗口只补跑 1 次。

## 三、类型、文件与状态真源

### 3.1 配置真源

Agent 级心跳策略文件：

```text
~/.tmagent/identities/agents/<agent_id>/heartbeat_policy.json
```

当前配置模型使用 `HeartbeatPolicy`，核心字段包括：

- `enabled`
- `cadenceMs`
- `startupGraceMs`
- `coalesceMs`
- `activeHours`
- `watchModules`
- `actionableRules`
- `deliveryPolicy`
- `llmEscalation`
- `maintenancePolicy`
- `instructionPath`

### 3.2 补充指令文件

```text
~/.tmagent/identities/agents/<agent_id>/HEARTBEAT.md
```

语义说明：

1. 它不再决定“多久跑一次、是否静默、哪些变化算关键变化”。
2. 它只在后台升级到 LLM 时，作为额外提示词拼入升级 prompt。

### 3.3 运行时状态真源

SQLite `app_state`：

```text
heartbeat_runtime:<agent_id>
```

当前运行态不再使用旧文件态心跳状态作为事实真源。

运行时状态包含：

- `laneState`
- `lastSnapshot`
- `lastSnapshotDigest`
- `lastScheduledAtUtc`
- `lastStartedAtUtc`
- `lastCompletedAtUtc`
- `nextDueAtUtc`
- `lastDecision`
- `lastSummaryDigest`
- `lastDeliveredAtUtc`
- `pendingTicket`
- `lastDeferredReason`
- `providerState`
- `pulseState`
- `interruptedRun`

## 四、执行链路

### 4.1 Ticket 入口

心跳不再直接“发起一轮聊天消息”，而是先创建后台 ticket。

当前支持的 ticket 类型：

- `auto`
- `manual`
- `recovery`
- `event_driven`

典型事件源：

- cadence 到点
- 手动巡检
- `delegate_job_settled`
- `provider_recovered`
- 重启后补跑

### 4.2 Defer 规则

以下情况不会丢弃 ticket，而是进入 `deferred`：

1. lane 正在运行
2. Agent 被 suppress（例如委派子代理进行中）
3. 当前不在 active hours
4. Provider 为 `down`
5. 启动缓冲期未结束

### 4.3 巡检流程

每轮后台心跳按如下顺序执行：

1. 采样快照：`provider / delegate / pulse / scheduler / memory`
2. 由 `HeartbeatDecisionEngine` 判定：
   - `noop`
   - `maintain_only`
   - `escalate`
3. 先执行 `maintenance`
4. 若需要，再执行 `escalation`
5. 若产出用户摘要，再单独调用主会话投递路径
6. 更新 `heartbeat_runtime:*` 与下一次 `nextDueAtUtc`

### 4.4 用户可见规则

自动心跳默认不进入会话历史。  
只有当 `deliverToUser=true` 时，才通过 `ConversationService::deliverHeartbeatSummary(...)` 把最终摘要写入主会话。

这意味着：

1. 主会话里不再出现后台心跳内部 prompt。
2. 不再需要通过旧的隐藏消息 clientMessageId 方案执行后台巡检。
3. 历史消息过滤逻辑不再依赖旧心跳特判。

## 五、关键变化判定

`HeartbeatDecisionEngine` 默认把以下信号视为关键变化：

- 委派任务新增、完成、失败、阻塞
- Provider 进入 `down / degraded / recovered`
- Pulse 进入 `soft_timeout / stalled / hard_timeout` 或从异常恢复到 `healthy`
- Scheduler 执行异常
- Memory 维护异常

默认不直接升级为用户摘要的内容：

- 普通 memory 增长
- 普通 scheduler 数量变化
- 无动作价值的快照抖动

手动巡检是特例：

1. 总是允许升级到 LLM。
2. 总是允许产出可见结果。
3. 即使无关键变化，也可以明确返回“当前无关键变化”。

## 六、与其他子系统的边界

### 6.1 HealthMonitor

- 只负责 Provider 健康探测与恢复事件。
- 不再直接发起聊天式心跳。
- Provider `down` 时，心跳 ticket 保留为 deferred。
- Provider `recovered` 时，会创建高优先级 `event_driven` ticket。

### 6.2 AgentPulse

- 只负责活性/超时状态。
- `pulse.hard_timeout` 会通过规则层转化为关键变化。
- Pulse 自身不是心跳调度器。

### 6.3 SchedulerService

- 只负责精准到点任务。
- 定时任务仍走各自调度与执行链路。
- 普通 scheduler 数量变化只作上下文，不默认对用户可见。

### 6.4 ConversationService / AgentRuntime

- 自动心跳不再调用 `enqueueUserMessageAs(...)`。
- 后台升级通过 `AgentRuntime::runBackgroundTask(...)` 执行。
- 主会话只承载最终摘要，不承载后台内部执行过程。

## 七、重启恢复规则

当前实现采用“恢复状态与意图，不恢复旧执行上下文”的策略。

应用启动时：

1. 加载 `HeartbeatPolicy`
2. 加载 `heartbeat_runtime:<agentId>`
3. 恢复 `pendingTicket / deferred / interruptedRun`
4. 若 `nextDueAtUtc <= startupTime`，在 `startupGraceMs` 后补跑 1 次

强约束：

1. 即使错过多个窗口，也只补跑 1 次。
2. 若启动时 Provider 仍为 `down`，补跑不会丢失，而是继续 deferred。
3. 若当前不在 active hours，则直接推进到下一个有效窗口。
4. 使用 `lastSummaryDigest` 防止重启后重复投递同一摘要。

- 最近延后原因
- 是否存在待处理 ticket
- Provider 状态
- Lane 状态
- 最后决策

## 九、事件口径

当前实现使用的新事件族：

- `heartbeat.ticket_created`
- `heartbeat.deferred`
- `heartbeat.cycle_started`
- `heartbeat.maintenance_completed`
- `heartbeat.escalation_started`
- `heartbeat.escalation_completed`
- `heartbeat.summary_delivered`
- `heartbeat.cycle_completed`
- `heartbeat.failed`

不再使用旧口径：

- `heartbeat.triggered`
- `heartbeat.completed`
- `heartbeat.skipped`
