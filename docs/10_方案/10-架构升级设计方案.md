## 一、方案总览

### 1.1 当前架构核心问题（4 位架构师共识）

| 编号 | 问题 | 严重度 | 来源 |
|------|------|--------|------|
| P1 | ChatService 演变为 God Object（~1626 行） | 高 | 系统架构师 |
| P2 | 单文件巨型 JSON 存储（chat_sessions.json） | 高 | 存储架构师 |
| P3 | 非原子写入，崩溃可致数据丢失 | 高 | 存储架构师 |
| P4 | 回合状态机隐式嵌入，无显式 Turn 状态 | 高 | 系统架构师 |
| P5 | 无 trace_id 贯穿，事件无 identity 归属 | 高 | 可观测性架构师 |
| P6 | 消息路由缺失，群聊只激活第一个 Agent | 高 | 协作架构师 |
| P7 | Pipeline 按 Session 1:1 绑定，不支持多 Agent 并发 | 高 | 协作架构师 |
| P8 | 流式状态绑定在 Session 上，多 Agent 会互相覆盖 | 高 | 协作架构师 |
| P9 | Identity ID 每次加载重新生成，需 identityIdMap 重映射 | 中 | 存储架构师 |
| P10 | io_history 与 messages 冗余存储 | 中 | 存储架构师 |
| P11 | 无持久化事件日志，进程退出即丢失 | 中 | 可观测性架构师 |
| P12 | ToolLogWidget 无按 session/identity 过滤能力 | 中 | 可观测性架构师 |

### 1.2 主方案：渐进式拆分 + 多文件存储 + 协作组件注入

**核心思路**：在现有 Identity-Session-Message 模型基础上，分 3 条线并行推进：

```
线路 A（系统+存储）：ChatService 瘦身 + 多文件目录存储
线路 B（协作）    ：MessageRouter + GroupTurnScheduler + ConcurrencyController
线路 C（可观测性）：TraceContext + EventLogger + MetricsCollector
```

**模块边界图**：

```

├─────────────────────────────────────────────────────────────────────┤
│                       Service 层                                     │
│                                                                      │
│  ChatService (瘦身版)                                                │
│  ├── TurnManager          回合状态机 + 队列管理 + 插话打断           │
│  ├── MessageRouter         消息路由决策（群聊 @机制）                │
│  ├── GroupTurnScheduler    群聊多 Agent 调度（并发请求+顺序渲染）    │
│  ├── ConcurrencyController 三层并发配额（全局/Agent/Provider）       │

**关键设计决策汇总**：

| 维度 | 决策 | 理由 |
|------|------|------|
| 存储格式 | 多文件目录 + JSONL 消息流 | 消除单文件瓶颈，支持追加写入 |
| 存储路径 | ~/.tmagent/ | 数据与应用分离，不受更新影响 |
| Pipeline 模型 | (sessionId, agentId) 复合键 | 支持群聊多 Agent 并发 |
| 多 Agent 调度 | 并发请求 + 顺序渲染（策略 C） | 兼顾速度和 UI 清晰度 |
| 消息路由 | MessageRouter 作为 ChatService 内部组件 | 避免新全局单例 |
| 打断机制 | 区分全局打断和定向打断 | 精确控制，避免误伤 |
| 回合状态 | 显式 TurnStatus 枚举（6 状态） | 替代隐式 hasActiveTurn 布尔值 |
| 消息状态 | 6 状态（Pending/Streaming/Completed/Cancelled/Interrupted/Error） | 区分主动停止与插话打断 |
| Trace 模型 | request_trace_id（入口生成）+ turn_id/run_id（执行级） | 避免 run 级 ID 冒充链路级 Trace |
| 事件日志 | JSONL 格式，按日期轮转 | grep 友好，崩溃安全 |

### 1.3 备选方案 A：MessageRouter 中枢模式

**核心差异**：引入 MessageRouter 作为独立全局单例，ChatService 退化为 UI 薄适配层。

```
UI → ChatService (薄适配层) → MessageRouter (核心路由中枢)
                                    │
                              ┌─────┼─────┐
                              ▼     ▼     ▼
                         AgentRuntime  AgentRuntime  ...
```

| 优点 | 缺点 |
|------|------|
| 架构更清晰，职责分离更彻底 | 改动范围大，需重构 ChatService 大部分逻辑 |
| 天然支持群聊 @机制和多 Agent 路由 | 引入新全局单例和中间层 |
| 为插件系统（阶段 7）做好准备 | 阶段 3 之前不需要全部能力 |

**取舍**：如果团队有充足时间做一次性重构，且确定阶段 7 插件系统需要 MessageRouter，可选此方案。否则主方案的渐进式拆分风险更低。

### 1.4 备选方案 B：SQLite 统一存储

**核心差异**：用 SQLite 替代 JSON/JSONL 文件存储。

| 优点 | 缺点 |
|------|------|
| 原子事务天然支持（BEGIN/COMMIT/ROLLBACK） | 引入 SQLite 依赖（需额外配置） |
| 查询能力强（按时间/Agent/关键词搜索） | 消息不再是人类可读文本文件 |
| FTS5 全文搜索为阶段 6 知识库做准备 | 与"可直接查看文本文件排障"需求冲突 |
| 并发写入由 SQLite WAL 模式处理 | 迁移复杂度更高 |

**取舍**：不把 SQLite 扩大成“所有业务数据的唯一真源”方案；当前主线已经把会话、事件与运行时状态切到 SQLite 主链，但记忆 Markdown、配置文件与少量可读文件仍按各自职责保留。也就是说，当前取舍不再是“继续双写过渡”，而是“状态主链 SQLite、文档真源 Markdown、配置真源文件化”。

**现状回写（2026-03-15）**：主线代码已完成会话、身份、消息、事件、pending turns、`currentSessionId`、`tabState`、任务状态与心跳运行时状态的 SQLite-first 收口，正常写入已不再依赖 JSON/JSONL；旧路径仅用于 legacy 导入、一次性回填与极少量排障兼容。当前判定应更新为“SQLite 主链已完成，legacy 迁移链保留”，而非“仍处于 JSONL + SQLite 双写过渡态”。

## 二、推荐目录树 ~/.tmagent/ 及文件字段定义

### 2.1 设计原则

1. **数据与应用分离**：所有用户数据存储在 `~/.tmagent/`，不受应用更新影响
2. **按实体分目录**：每个 Agent 独立目录、每个 Session 独立目录，避免单文件瓶颈
3. **按职责分目录**：配置、身份、会话、日志各自独立
4. **版本化**：根目录 `manifest.json` 记录全局版本，支持迁移
5. **可恢复写入**：结构化 JSON 使用 write-tmp-replace，JSONL 使用 append + flush + 批量 fsync

### 2.2 完整目录树

> 口径补记（2026-03-16）：当前实现已切到 SQLite-first。
> 下面的目录树保留“可读落盘 + 兼容回退”视角：`config/app_state.json` 仅保留 UI / Tab 恢复快照，
> `task_state:*`、`heartbeat_state:*` 与 `pending_turns` 等运行时状态已迁入 SQLite 主链；legacy 文件仅用于迁移读取或兼容回退。

### 2.4 记忆提炼与淘汰策略（Memory Lifecycle）

| 阶段 | 输入 | 输出 | 默认策略 |
|------|------|------|----------|
| Retain | 完成态消息（`Completed`） | daily log + memory.md 候选 | 每轮提取 2-5 条候选，优先写 daily log |
| Recall | 当前问题 + 关键词 | 注入片段/检索片段 | 默认注入 `soul.md + identity.md + user.md + memory.md`；daily log 按需检索 |
| Reflect | 每日/每批次日志 | memory.md 更新 | 每 20 条日志触发一次提炼，更新长期记忆 |
| Forget | 过旧低价值日志 | 归档/清理 | daily log 默认 90 天归档，memory.md 仅人工或反思流程删改 |

> 约束：`Interrupted/Cancelled/Error` 默认不进入 Retain，避免把中断噪声写入长期记忆。
> 约束：SQLite/向量索引是派生数据，损坏后可由 Markdown 真源重建。

## 三、消息/回合/工具事件的状态机与时序图

### 3.1 消息状态机（Message Status）

```
                    ┌──────────┐
                    │ Pending  │
                    └────┬─────┘
                         │
            ┌────────────┴────────────┐
            │                         │
            ▼                         ▼
     ┌───────────┐               ┌──────────┐
     │ Completed │               │Streaming │
     │ (用户消息 │               │(助手消息)│
     │  直接完成)│               └────┬─────┘
     └───────────┘                    │
               ┌───────────┬────────────┬──────────────┬───────┐
               │           │            │              │
               ▼           ▼            ▼              ▼
        ┌──────────┐ ┌───────────┐ ┌────────────┐ ┌───────┐
        │Completed │ │Cancelled  │ │Interrupted │ │ Error │
        │(流式完成)│ │(主动停止) │ │(插话打断)  │ │(失败) │
        └──────────┘ └───────────┘ └────────────┘ └───────┘
```

| 状态 | 触发条件 | 可转换到 | 备注 |
|------|---------|---------|------|
| Pending | 消息创建时 | Streaming, Completed, Error | 用户消息创建后直接 → Completed |
| Streaming | LLM 开始返回 delta | Completed, Cancelled, Interrupted, Error | 仅 assistant 消息 |
| Completed | 流式结束/用户消息发送成功 | (终态) | 不可逆 |
| Cancelled | 用户主动点击停止 | (终态) | 由用户主动终止 |
| Interrupted | 被新消息抢占/定向打断 | (终态) | 保留已接收部分，但默认不注入下一轮上下文 |
| Error | 网络错误/LLM 错误 | (终态) | 记录错误信息 |

    ├─ 开发者、测试员：不受影响，继续执行
    ├─ 写入用户新消息（mentions=[架构师]）
    ├─ MessageRouter 路由：只激活架构师重新响应
    └─ 架构师重新开始 LLM 请求（新上下文默认不含被中断片段）
```

### 3.8 @路由决策树

```
消息进入 Session
│
├── Private Session
│   └── 发送者是用户 → 激活对方 Agent（行为不变）
│
└── Group Session
    ├── 群聊已归档 → 不激活任何 Agent
    ├── mentions 包含 "@all" → 激活所有 Agent 参与者
    ├── mentions 包含具体 Agent ID → 只激活被 @的 Agent
    ├── mentions 为空 + 发送者是用户 → 默认 @all
    └── mentions 为空 + 发送者是 Agent → 不激活（防无限循环）
```

**防循环机制**：同一 trace_id 下，同一 Agent 最多被激活 N 次（默认 3），复用现有工具链循环熔断机制。

### 3.9 回滚边界与 Checkpoint 规则

1. 每次 LLM 请求开始前写入 checkpoint：`{turnId, runId, lastStableSeq}`。
2. `abortAndRollback()` 只回滚到最近 checkpoint，不回滚已稳定落盘的用户消息。
3. 已落盘 `tool_result` 不删除，只追加 `status=Interrupted` 的补偿事件，保证审计可追溯。
4. 上下文构建默认仅加载 `status in [Completed]` 的 assistant/tool 消息；`Interrupted/Cancelled/Error` 仅在“用户显式引用”模式下参与。

### 3.10 字段命名与事件 Schema 约定

1. 存储层（`messages.jsonl`、`meta.json`）统一 `camelCase`。
2. 可观测事件层（`events-*.jsonl`）统一 `snake_case`。
3. `events-*.jsonl` 每条事件增加 `event_schema_version`，便于后续演进与兼容解析。
4. `trace_id` 只用于链路关联；`turn_id` 用于回合关联；`run_id` 用于一次执行关联，三者不互相复用。

## 四、原子写、并发写、崩溃恢复策略

### 4.1 原子写策略：write-tmp-replace

所有结构化文件（JSON）的写入遵循四步法：

```
1. 写入同目录临时文件：{target}.tmp.{uuid}
2. flush + fsync 文件内容（Windows: FlushFileBuffers, Linux: fsync）
3. 原子替换目标文件：
   - Linux/macOS：rename(tmpPath, targetPath)
   - Windows：MoveFileEx(..., MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH) 或 QSaveFile::commit()
4. （POSIX）fsync 目标目录，确保目录项持久化
```

JSONL 消息文件使用追加写入（append + flush），并按策略执行批量 fsync（默认每 16 条或 1 秒）。

### 4.2 各文件写入策略汇总

> 补记（2026-03-16）：以下表格仍保留文件侧写入策略，便于理解历史设计与兼容回退路径。
> 当前代码已对 `tabState` / `currentSessionId` / `task_state:*` / `heartbeat_state:*` / `pending_turns`
> 采用 SQLite-first；对应文件更多承担兼容快照或 legacy 读取职责。

| 文件 | 写入模式 | 频率 | 策略 |
|------|----------|------|------|
| manifest.json | 全量覆写 | 低（启动/关闭） | write-tmp-replace |
| config/app_state.json（兼容快照） | 全量覆写 | 中（Tab 切换 / 回退写入） | write-tmp-replace，节流 5s |
| identities/user.json | 全量覆写 | 低（配置变更） | write-tmp-replace |
| identities/agents/*/profile.json | 全量覆写 | 低（配置变更） | write-tmp-replace |
| identities/agents/*/runtime.json | 全量覆写 | 中（运行态变更） | write-tmp-replace，节流 1s |
| user.md | 覆写/分段更新 | 中（用户画像变化） | write-tmp-replace |
| identities/agents/*/{soul,identity,memory}.md | 覆写/分段更新 | 中（配置/反思） | write-tmp-replace |
| identities/agents/*/memory/*.md | 追加写入 | 中（每轮） | append + flush，批量 fsync |
| sessions/index.json | 全量覆写 | 中（新建/删除会话） | write-tmp-replace，节流 2s |
| sessions/data/*/meta.json | 全量覆写 | 低 | write-tmp-replace |
| **sessions/data/*/messages.jsonl** | **追加写入** | **高（每条消息）** | **append + flush，关键事件立即 fsync，普通事件批量 fsync** |
| sessions/data/*/pending_turns.json（兼容回退） | 全量覆写 | 中 | write-tmp-replace |
| logs/events-*.jsonl | 追加写入 | 高 | append + flush |

### 4.2.1 关键事件立即 fsync 清单

以下事件写入后必须立即 fsync，不参与批量延迟刷盘：
1. 用户消息落盘（`message.user_sent` / `messages.jsonl` 的 user 行）
2. 回合终态事件（`turn.completed` / `turn.cancelled` / `turn.interrupted` / `turn.failed`）
3. 会话结构变更（新建会话、删除会话、参与者变更）
4. Agent 关键配置变更（模型、提示词、岗位、权限）

其余流式增量（delta、普通工具日志）允许批量 fsync。

### 4.3 写入节流（Throttle）

高频写入使用 QTimer 单次触发节流，合并短时间内的多次写入：
- `sessions/index.json`：2 秒节流
- `config/app_state.json`（兼容快照）：5 秒节流
- 应用退出时 `forceFlush()` 强制刷盘

### 4.4 并发写策略

**核心原则**：文件粒度隔离 + 同文件单写器（single-writer）。

| 场景 | 写入目标 | 冲突？ | 解决方案 |
|------|----------|--------|---------|
| 群聊同一 Session 多 Agent 同时流式输出 | 同一 `sessions/data/*/messages.jsonl` | **有冲突** | `SessionMessageWriter`（按 sessionId 单写队列串行 append） |
| 同一 Agent 多 Session | 不同 Session 目录 | 无冲突 | 不同文件，天然并行 |
| 用户操作 + Agent 输出 | `app_state.json` + `messages.jsonl` | 低冲突 | `app_state` 走 `PersistenceManager`，消息走 `SessionMessageWriter` |
| 多操作同时更新索引 | sessions/index.json | **需序列化** | PersistenceManager 单入口 + 节流合并 |

**PersistenceManager** 负责结构化文件序列化写入；`SessionMessageWriter` 负责每个 Session 的消息单写流水线。

### 4.5 崩溃恢复策略

#### 崩溃场景与恢复矩阵

| 崩溃时机 | 恢复策略 | 数据损失 |
|----------|----------|----------|
| 写 messages.jsonl 中途 | 检测最后一行完整性，截断不完整行 | 最多丢失最近一个未 fsync 批次（默认 ≤16 条或 ≤1 秒） |
| write-tmp-replace 步骤 1（写 tmp） | 启动时清理 tmp/ 残留 | 无（原文件未修改） |
| write-tmp-replace 步骤 3（原子替换） | replace 是原子的 | 无 |
| 创建 Session 目录中途 | 检测缺少 meta.json 的目录，清理 | 最多 1 个空 Session |
| index.json 损坏 | 从 sessions/data/ 的 meta.json 重建 | 无 |
| events-*.jsonl 写入中途 | 截断不完整行 | 最多丢失最近一个未 fsync 批次 |

#### 启动时恢复流程

```
应用启动
  ├── 1. 清理 tmp/ 目录中的残留临时文件
  ├── 2. 检查 manifest.json → 需要迁移则执行
  ├── 3. 加载 Identity 文件（user.json + agents/）
  ├── 4. 加载 Session 索引，校验与 data/ 目录一致性
  │     ├── index 中有但 data/ 中无 → 从 index 移除（孤儿索引清理）
  │     └── data/ 中有但 index 中无 → 从 meta.json 重建索引条目
  ├── 5. 检查每个 messages.jsonl 最后一行完整性 → 截断不完整行
  ├── 6. 优先从 SQLite 恢复 pending_turns / 运行时状态；命中 legacy 文件时回填后再入队
  └── 7. 恢复 SQLite `app_state` 中的当前会话 / Tab 状态；仅在缺失时回退读取 `app_state.json`
```

#### 诊断快照

异常状态时自动生成诊断快照到 `~/.tmagent/logs/diagnostics/`：
- 触发条件：应用崩溃、turn 超过 5 分钟未完成、队列深度超过 10、内存增长超过 20%
- 快照内容：所有活跃 Pipeline 状态、Runtime 状态、队列深度、内存使用、最近 20 条事件

## 五、分阶段迁移计划

### 5.1 总体策略

迁移分为 3 个子阶段 + 2 个功能阶段，每步保持功能等价，可独立发布和回滚。

### 5.2 子阶段 A：引入 AtomicFileWriter（极低风险）

## 六、验收标准

### 6.1 架构正确性

| 验收项 | 标准 | 验证方法 |
|--------|------|---------|
| 单一事实源 | Session::messages 是消息的唯一权威数据源，io_history 废弃 | 代码审查：无任何路径绕过 messages 直接读写 io_history |
| UI 解耦 | IdentityView 不直接访问 AgentRuntime，通过信号/槽通信 | 代码审查：IdentityView 无 AgentRuntime 头文件引用 |
| 模块边界 | ChatService 行数 < 800（从 1626 行瘦身） | 代码统计 |
| Turn 状态机 | 所有状态转换通过 TurnManager 的显式方法，无散布逻辑 | 代码审查 + 状态转换覆盖测试 |
| 层次隔离 | Service 层不直接操作 QWidget；Model 层不依赖 Service 层 | 编译依赖分析 |

### 6.2 功能正确性

| 验收项 | 标准 | 验证方法 |
|--------|------|---------|
| 插话有效 | 用户发新消息后 ≤200ms 旧回合被打断，新回合开始 | 自动化测试：发送消息 → 等待流式开始 → 发送新消息 → 验证旧 turn interrupted |
| 连续发言不丢 | 运行中连续发送消息全部入队，不因背压被拒绝 | 自动化测试：流式中连续发送 20 条 → 验证 queue size=20 且全部最终出队 |
| 群聊 @可控 | @特定 Agent 只激活该 Agent，@all 激活所有 | 自动化测试：发送 @消息 → 验证 RouteResult.targetAgentIds |
| 多助手不串数据 | Agent A/B 输出在同一会话文件内按 `senderId` 正确归属，不发生身份串写 | 自动化测试：两个 Agent 并发响应 → 验证每条消息的 senderId/turnId/traceId 一致性 |
| 定向打断 | 群聊中 @某 Agent 发新消息只中断该 Agent | 自动化测试：3 Agent 并发 → @其中 1 个 → 验证只有 1 个被中断 |
| 防循环 | Agent 间 @链式调用不超过 N 次 | 自动化测试：设置 N=2 → Agent A @B @A → 验证第 3 次被熔断 |
| Private 不受影响 | 所有群聊改动不影响 Private Session 行为 | 回归测试：Private Session 的全部现有测试用例通过 |

### 6.3 数据正确性

> 口径补记（2026-03-16）：当前消息主链已切到 SQLite-first。
> 因此本节关于“消息顺序/损坏/恢复”的验收，以 SQLite `messages` 表和相关查询链路为准；
> `messages.jsonl` 仅保留迁移读取与兼容回退，不再作为主门禁事实源。

| 验收项 | 标准 | 验证方法 |
|--------|------|---------|
| 重启可恢复 | 应用重启后所有会话、消息、Agent 配置完整恢复 | 测试：写入数据 → 重启 → 验证数据一致 |
| 消息主链可读 | SQLite `messages` 主链与日志查询链路可直接反查消息、turn/trace/tool 字段；legacy `messages.jsonl` 仅作兼容回退 | 自动化测试 + 命令行查询验证 |
| 版本可迁移 | schemaVersion 2 的数据可自动迁移到 3 | 测试：准备 v2 数据 → 启动应用 → 验证迁移成功 + 数据完整 |
| 迁移可回滚 | 迁移失败时自动回滚，旧数据不受影响 | 测试：模拟迁移失败 → 验证旧文件完好 |
| 崩溃安全 | 任意时刻 kill 进程，重启后关键事件不丢；普通消息主链不出现部分写入导致的半记录 | 测试：循环写入 + 随机 kill → 统计数据损失 |
| 写入完整性 | 消息主链在并发写入下不丢消息、逻辑顺序可恢复，不出现半行/半记录污染 | 自动化测试：并发写入同一 session → 验证总数、seq 顺序与 payload 完整性 |

### 6.4 运维友好性

| 验收项 | 标准 | 验证方法 |
|--------|------|---------|
| session_id 定位 | `grep "session_id":"SESS" events.jsonl` 可找到该会话所有事件 | 手动验证 |
| trace_id 定位 | `grep "trace_id":"TRACE" events.jsonl` 可还原完整执行链路 | 手动验证 |
| 排障速查 | 提供排障命令速查表，覆盖 8 种常见场景 | 文档审查 |
| 日志轮转 | 事件日志按日期轮转，单文件 ≤ 50MB，保留 14 天 | 配置验证 + 长期运行测试 |
| 诊断快照 | 异常时自动生成快照，包含足够排障信息 | 模拟异常 → 验证快照内容 |

### 6.5 性能边界

| 指标 | 目标值 | 告警阈值 |
|------|--------|---------|
| Turn 端到端延迟 | P50 < 5s, P95 < 30s | P95 > 60s |
| LLM TTFT（首 token） | P50 < 1s, P95 < 3s | P95 > 5s |
| 工具调用延迟 | P50 < 100ms, P95 < 2s | P95 > 10s |
| Tab 切换延迟 | ≤ 200ms | > 500ms |
| UI 帧率 | ≥ 30 FPS | < 15 FPS |
| 并发 Agent 数 | ≤ 8 | > 12 |
| 消息文件追加延迟 | < 5ms | > 50ms |
| 事件日志写入延迟 | < 10ms | > 100ms |

**退化保护**：
- UI 帧率 < 15 FPS → 后台 Tab 暂停 UI 更新
- UI 帧率 < 10 FPS → 前台降级为纯文本渲染
- 队列深度 > 10 → 启用软背压（继续入队 + UI 提示预计等待 + 支持取消排队项）
- 队列深度 > 200 → 启用硬保护（拒绝新入队并提示“队列已满，请取消部分排队任务后重试”）
- 事件日志写入延迟 > 100ms → 降级为异步批量写入

### 6.6 故障注入（Chaos）验收

| 场景 | 注入方式 | 期望结果 |
|------|----------|----------|
| 并发写冲突 | 群聊 3 Agent 同时流式 + 高频用户插话 | `messages.jsonl` 无乱序/半行；`seq` 连续递增 |
| 进程随机中断 | 写入中每 1-3 秒随机 kill 进程 | 重启后索引可恢复；数据损失不超过未 fsync 批次 |
| 网络抖动 | 模拟 5%-20% 请求超时/断连 | turn 进入 `Failed/Interrupted`，无僵尸 turn |
| 工具长阻塞 | 人工注入 30s 工具调用 | 用户插话可打断；队列可继续推进 |

## 七、优化项与未决风险

### 7.1 P0（必须先做，避免返工）

| 项 | 现状风险 | 约束要求 |
|----|----------|----------|
| 打断语义 | `Cancelled/Interrupted` 容易混用 | 插话统一 `Interrupted`；主动停止统一 `Cancelled` |
| 回滚边界 | 实现可能“误删已落盘消息” | 只回滚到 checkpoint，已稳定落盘消息只做补偿标记 |
| Trace 字段 | run/turn/trace 混用风险 | 三层 ID 不复用；事件强制带 `event_schema_version` |

### 7.2 P1（建议本阶段补齐）

| 项 | 目标 |
|----|------|
| 背压治理 | 软背压 + 硬上限，兼顾连续发言体验和内存安全 |
| 关键事件落盘 | 用户消息与 turn 终态立即 fsync，确保故障后可追溯 |
| 记忆治理 | 提取、去重、提炼、TTL 全流程标准化 |

### 7.3 安全与隐私最小基线

1. API Key 与令牌不落明文日志；日志中统一掩码（前 6 后 4）。
2. 头像与附件路径写入前做路径规范化，拒绝目录穿越。
3. 导出诊断包默认脱敏（用户名、绝对路径、提示词中的密钥片段）。
4. `~/.tmagent/backups/` 默认保留 7 天，支持一键清理。

### 7.4 何时允许进入阶段三

1. 6.2 与 6.3 验收全通过。
2. 6.6 的 4 类 Chaos 场景连续 3 轮稳定通过。
3. 打断链路在 1080P 常规机器上 P95 < 200ms。

## 八、记忆系统统一路线（整合 OpenClaw）

### 8.1 单一口径（本项目后续唯一遵循）

1. 记忆真源使用 Markdown 文档：`user.md`、`soul.md`、`identity.md`、`memory.md`、`memory/YYYY-MM-DD.md`。
2. `sessions/messages.jsonl` 与 `logs/events-*.jsonl` 仅承担执行审计与回放，不作为长期人格记忆真源。
3. SQLite/向量库仅为检索加速的派生索引，随时可从 Markdown 重建。
4. 记忆写入默认只接受 `Completed` 回合结果；`Interrupted/Cancelled/Error` 不入长期记忆。
5. 所有记忆更新必须可追溯：写入事件记录 `trace_id`、`turn_id`、`agent_id`。

### 8.2 注入与检索策略（避免“假记忆”）

1. 每轮固定注入：`soul.md + identity.md + user.md + memory.md`（按 token 预算截断）。
2. 每日日志不全量注入，改为按需检索（关键词或 FTS）后注入片段。
3. 当上下文接近上限，先触发“预压缩记忆 flush”，再执行 compact。
4. 若用户明确说“记住这个”，强制写入 `memory.md` 并回执一条 `memory.updated` 事件。

### 8.3 与愿景路线图的阶段对齐

1. 阶段 5（智能化记忆）优先完成 Markdown 真源 + Retain/Recall/Reflect 闭环。
2. 阶段 6（资源库体系）再引入 FTS5/向量检索与共享知识库，不提前把 SQLite 作为主存储。
3. 阶段 7（插件系统）只消费统一记忆接口，不直接读写底层记忆文件。

### 8.4 统一验收标准（记忆专项）

1. 关闭并重启应用后，Agent 能稳定读取同一套 Markdown 记忆并保持行为一致。
2. 通过 session_id/trace_id 可以定位“哪条对话写入了哪条记忆”。
3. 删除会话不会删除身份记忆；删除助手会连带删除该助手记忆目录。
4. 当索引损坏时，可在不丢失 Markdown 的前提下完成重建并恢复检索能力。
